# 08 - 预览图与对象框：经验总结

> 这篇不记单个坑，记**方法与教训**：为什么这一轮改了七八版才收口，哪些推理靠得住、
> 哪些必须实测，以及下次遇到"二进制格式 + 消费端黑盒"这类问题该怎么走。
> 结论口径见 [07-自产预览图方案.md](07-自产预览图方案.md)；像素级机制见 [06](06-VSDX缩略图与嵌入呈现图.md)。

## 1. 最终口径（可直接照抄）

| 约束 | 取值 | 为什么 |
| --- | --- | --- |
| 声明尺寸（`rclFrame`） | `画布 × (LogicalDpi ÷ 参考dpi)` | 这是"帧不移动"的自洽式，七组样本验过 |
| `LogicalDpi` / 参考dpi | **常规值且两轴同值**：参考固定 144dpi、逻辑固定 120；代码护栏 `previewDpiOutOfBand` 卡 [96,160] 与两轴 10% 差 | dpi 不是可调量：按对象压到 64 以下、或按分轴算成 57/600/1992，都会撑大对象框（踩过两次） |
| 画面自然尺寸 | **必须等于声明尺寸**（画面像素 = 画布in × 逻辑dpi） | 消费端把**声明矩形**映射到对象框上：内容只有声明的 28% 时只占框一角（没铺满/偏左上 ✗），反过来就"只有一部分/偏右下" ✗ —— 一条根因解释四种现象 |
| 声明 ≠ 对象框 | 相差 ≥5% | 相等时必然被撑大（T1b 样本） |
| 内嵌 vsdx 页面 | **不动**（`patchPageSize` 默认 false） | `pages.xml` 是生成侧给的权威画布；按包围盒压小会让框缩水、内容落到页面外 |

实现落点：`packages/postprocess/src/preview.ts`（`makePreviewEmf` / `pickTemplate` / `readPreviewMetrics`
/ `checkPreviewConsistency`）、`packages/postprocess/src/embed.ts`（接入与护栏）、
模板生成 `packages/postprocess/scripts/make-preview-template.ps1`。

## 2. 这一轮为什么慢：三条推理，一条对的都没有

1. **"声明尺寸 = 画面自然尺寸"这条我没验就当成显然** —— 实际是踩了"只挑自然 ≤ 声明"的近似，
   结果小图底边线被裁、大图右侧被裁。**布局必须按等式算，不能靠"接近"**。
   后续（2026-09-28）还发现这条**连方向都记偏了**：真正决定观感的是"自然 vs **对象框**"，
   "自然 = 声明"只是在 `L ≈ 120` 时恰好三条重合、看起来对 ✗。
2. **把代数自洽当成了充分条件，还把 dpi 当成了自由变量** —— 自洽式保证"帧不移动"，
   但**不保证 dpi 值本身安全**。为了让"自然 = 声明"成立，我取 `LogicalDpi = 画面像素 ÷ 画布in`：
   经典四图上算出 93~133（看起来没事 ✗），真实工程的扁图上直接炸到 **57 / 600 / 1992** ✗ ⇒ 框被放大。
   **公式只覆盖它拟合过的取值区间；为了让一条等式成立而去动一个"格式常规字段"，是最隐蔽的一类错**。
   现在这条由代码护栏 `previewDpiOutOfBand` 硬卡住，并有一条喂极端比例画布的回归用例。
3. **拿本地渲染器当 Word 的替身** —— `System.Drawing` 画 EMF 时按元文件自身 dpi 走，
   和 Word 的映射完全不同。我用它"看到"的画面去调参数，等于拿错尺子量。
   **视觉结论只能人眼验；本地渲染只能验"文件能不能解析"**。
4. **测试素材比例太单一** —— 一直用 block 1.1:1、flowchart 0.52:1、er 1.37:1、class 0.87:1 这四张，
   全在模板覆盖范围内 ✗，所以第 2 条的 bug 一直不显形；真实工程里 4:1~21:1 的图一上来就捅破。
   **自检素材要覆盖"极端"，不只是"典型"**。
5. **把"看着对"当成了"算对"** —— 中间几轮我用"预生成档位近似比例"顶事，本地指标一片绿 ✗，
   真正的判据（内容物理尺寸 = 声明尺寸）根本没进指标表 ⇒ 你打开就看到"没铺满/偏角/只有一部分" ✗。
   **先把变量表列全（画布/框/声明/像素/内容物理/文字/边框/坐标），每条给算式与合格线，再动手**。
6. **格式字段有"隐含精度"** —— 手写 EMR_EXTTEXTOUTW 的 `Dx` 步进数组是消费端的排版依据：
   按 0.55em 估，而 Microsoft YaHei 的 `m` 实测 1.25em、汉字 1.3333em ⇒ 英文叠字、汉字看着正常 ✗。
   **凡是"消费端会用到的数值"，都要实测，不要估**；参考设备同理（`254mm=10in` ⇒ 两轴都严格 144.00dpi）。

## 2.5 边界：哪些不归我们管

- **画布尺寸与比例是生产端口径**（mmd2vsdx 决定页面多大、什么形状）。本侧**不为其做适配**：
  不为极端比例增模板档、不按比例"优化"版式 —— 是什么样就是什么样 ✓。
  本侧只守两条：**画面不被裁**（挑档时两轴不超过对象框）+ **帧不移动**（自洽式）。
- 于是"极端扁图上占位画面偏小"是**预期表现**，不是缺陷；要改就得改生产端的画布/版式 ✓。
- 同理：**连线是否画出来**是生产端口径（本轮真 bug 在那边，已修 ✓）；本侧只做字节透明的搬运
  （实测：服务直出 8768B → 写进 docx 8768B，形状/Connect/master 逐项一致 ✓）。

## 3. 站得住的取证方法（这次真正解决问题的三条）

1. **拿标准样本对照字段布局**：手写 EMF 记录总被 GDI+ 拒解析，最后是打开 GDI+ 自己产出的
   模板件、逐字段打印 `EXTTEXTOUTW`（`rcl` 用空矩形、串不加 NUL、`offDx = 76 + 2n`），
   照抄才通。**遇到"我按规范写的却不被接受"，先去对照同源真实产物，而不是继续读文档**。
2. **二分定位而不是整体重写**：把记录按条切片、逐个组合喂给解析器（`只有注释` ✓ → `+边框` ✓ →
   `+字体` ✓ → `+一行文字` ✓ → `+两行` ✗），一次就锁定了是哪一段不合法。
3. **用消费者行为反推映射**：无法直接观察 Word 怎么摆放画面，就用两次"哪条边被裁"的观察反推出
   "按自然尺寸摆放 + 裁切"，再把这条当成硬约束写进代码。**黑盒不可见时，设计能分辨两种假设的观察**。
4. **护栏要能自动报**：`declaredEqualsFrame` 这类护栏早就在，每次出实例都打印，护栏一响就知道
   又踩到"声明 = 框"；没有它，这一轮的两次回退都要靠人发现。

## 4. 工程习惯上的教训

- **一次只改一个变量**：这一轮有两次把"页面修补"和"dpi 改写"一起改，出事后无法归因，只能整段回退；
- **改动要能整体回退**：每次提交一个可独立回退的改动，回退时用 `git revert` 留下记录，
  比手工改回去安全；
- **给人验的件要换名字**：同一路径反复覆盖，Word 还开着旧文件时会打架（这次就让一份验收件
  在导出时卡了 20 分钟）；
- **不要用 PowerShell 的 `Get-Content | Set-Content` 改中文源码**：会按 GBK 误读，把文件写坏
  （这次写坏过 `preview.ts`，靠 `git checkout` 救回）；
- **`git commit -m` 里别出现半角双引号**：会被 shell 拆成 pathspec，提交失败（已犯两次）；
- **分支名一律用 ASCII**：`feat/self-produced-preview`、`docs/emf-declared-size`。

## 5. 本次踩坑清单（现象 → 根因 → 结论）

| 现象 | 根因 | 结论 |
| --- | --- | --- |
| 双击后对象框巨大 | 声明尺寸 = 对象框；或 `LogicalDpi` 被改成非常规值 | 声明只认自洽式；dpi 只走常规值 |
| `class` 画布异常、框缩水到 184×130pt | `patchPageSize` 用"四格齐全"的包围盒压页面，77 个形状只算到 1 个 | 默认不修补页面 |
| 预览文字缩在角落 | 声明 15in 而画面自然 4in | 两者必须相等 |
| 预览文字被裁掉一部分 | 声明 0.82in 而画面自然 1in | 同上 |
| 文字右/底边线消失 | 画面自然尺寸大于声明尺寸，超出即被裁 | 同上，并按等式反算 `LogicalDpi` |
| 手写 EMF 一律报 "A generic error occurred in GDI+" | 多条文字记录 / 非空 `rcl` / 缺 `Dx` / 非 ASCII 串不带 NUL | 不走手写记录，用 GDI+ 生成的模板 |
| 画布尺寸静默读不到，框退化到 6×4.5in | cell 解析只认双引号固定顺序，生成侧用单引号 | 引号与属性顺序都不敏感（真 bug） |

## 6. 尚未证明

1. 跨 Word 版本、跨 Office 位数、跨机器未验（本轮全在单机单版本上）；
2. `LogicalDpi` 的安全区间只实测过 96~144（D1~D3、基准 120），93~133 是"同档推测"；
3. 模板比例档只到 0.5 / 0.667 / 1 / 1.5 / 2，极端长宽比（>3）会走最近档，画面会变形；
4. `stripVsdxThumbnail` 与 `DrawingSizeType` 的实际收益仍未单变量验证（本轮各次实验里没看到翻转）。
