# 12-Visio路线与无Visio路线的差异（含"改画布"方案）

> 用途：**区分"无 Visio 嵌入"与"有 Visio 嵌入"的结果差异**，并记录"走 Visio 时修正画布大小"这一步的目的、依据、实测数据与最小改动形态。
> 前置：11 号（非 Visio 路线的尺寸换算与参数说明）、10 号（Visio COM 归一化的口径）。
> 状态：**方案已定、实现待做**；实测数据均来自本机真实产物，标注"已确认"的可以直接引用，"待澄清"的必须先量。

## 1. 一句话差异

| 路线 | 画布（页面）是什么 | 预览件是什么 | 结果 |
| --- | --- | --- | --- |
| **无 Visio** | 生产端生成时留了约 10% 余量的页面 | 我们自产的示意 EMF（"虚线框 + 题注"） | 画布、件、框三者由我们的公式串起来；算不出走线，极端情况下连线会落在画布外——**这些都可接受** |
| **有 Visio** | 目前仍是同一个"带 10% 余量"的页面 | Visio 渲染的**真图** EMF | 件只覆盖**绘图内容范围**（含走线），页面却更大 ⇒ 初始框 ≠ 画布、双击后框被恢复到页面自然尺寸 ⇒ 现象是"余量被加回来、框变大" |

**10% 余量、自动连线、连线偶发越界，都是"无 Visio 路线"的妥协产物**：那条路上我们无法计算走线，只能靠留白兜底。有了 Visio，绘图范围变成**真值**（`Page.Export` 的边界包含走线），这个范围可以直接用。

## 2. 目标与限制

目标：走 Visio 时，**画布 = Visio 的真实导出范围**，于是

```
件声明（Visio 真图） = 画布 = 对象框
```

⇒ 初始预览就是画布本身，双击后 Visio 恢复的也是同一个尺寸 ⇒ **不变大、不留白、不裁切，且预览是真图**。

限制（用户口径）：

1. 不加节点、不改文档内容；
2. 不改 Visio 输出件（EMF）的字节；
3. 只用 Visio 官方接口；
4. 不留 Visio 进程、不阻塞；
5. 无 Visio 路线保持现状（它的妥协是可接受的）。

## 3. 已确认的实测数据（本机，2026-09-29）

样本：`05-flowchart-1.vsdx`（mmd2vsdx 产物）。

| 量 | 值 |
| --- | --- |
| 页面 | 1.6606 × 3.1731 in |
| 节点包围盒（Pin/Width 求并集） | 1.5000 × 2.8750 in（正好是页面的 90%，即那 10% 余量） |
| Visio 导出件的声明尺寸 | **0.9815 × 1.8516 in** |
| 声明 ÷ 节点包围盒 | 1.53 / 1.55（两轴一致） |

推论：**Visio 导出件用的不是页面英寸**，而是乘了一个页面比例因子（应为页面的 drawing scale）。所以"让件声明 = 页面尺寸"不能只把页面设成节点包围盒，必须把这个因子一起算进去。**这一项属于"待澄清"，实现前先量准。**

接口行为（同一批实测）：

| 调用 | 观察 |
| --- | --- |
| `Page.ResizeToFitContents()` | 页面**变大**（1.6606×3.1731 → 2.0104×3.3854in，它自加约 0.175in/边），节点**整体平移**、相对间距不变；导出件声明仍是绘图范围（≠ 页面）⇒ **这条路不成立** |
| `PageSheet` 的 `PageWidth/PageHeight` 赋值 | 生效（1.6606×3.1731 → 1.5000×2.8750in）⇒ **改画布可行** |
| `Page.CenterDrawing()` | 会平移内容，实测把部分节点推出页面（某节点 y = −0.32in，将被裁）⇒ **不能用它来定位** |
| 直接写节点的 `PinX/PinY` | **被拒**：节点来自带保护的模具，报"单元格受到保护"⇒ 平移前必须先临时解锁（`LockMoveX/LockMoveY` 置 0，或用 `Shape.Move`） |

## 4. 最小改动形态（待实现）

全在 `scripts/visio-normalize.ps1` 里、全在工作副本上，**只平移不缩放**（保证内部节点相对位置与现有坐标公式不受影响）：

```
1) 取内容范围：含走线的绘图范围（Visio 的 BoundingBox 接口，或导出件声明 × 页面比例因子）
2) 设页面尺寸 = 该范围（PageWidth / PageHeight）
3) 临时解锁 + 整体平移，让内容恰好落在页内（平移量 = 内容范围原点）
4) 再做原来的两件事：SaveAs（重存 vsdx）+ Page.Export（导出真图 EMF）
```

余量参数：默认 **0**（画布 = 内容范围本身）。若希望保留一点边距，加一个可配置项（例如 2%），但必须明白：边距越大，件声明与页面越难严格相等。

## 5. 已否掉的路（记下来，别再试）

| 方案 | 为什么否掉 |
| --- | --- |
| 改 Visio 件的字节（声明矩形 / 设备 dpi / 逻辑 dpi） | 深度干预别人的产物；实测分别导致"框被撑大"与"内容与声明对不上、靠左上留白" |
| 往页面里加整页白底形状，让导出覆盖整页 | 等于加节点、改内容，用户明确不允许 |
| `Page.ResizeToFitContents()` | 只会把页面撑大（自加余量），导出仍是绘图范围 |
| 对象框按"件"的尺寸定 | 会让初始框小于页面 ⇒ 双击后变大（就是当前要修的现象） |
| 对象框按"画布"定、件拉伸填满 | 件与页面比例不一致时产生形变 |

## 6. 改完的验收判据

| 判据 | 期望 |
| --- | --- |
| 件声明 vs 画布 | 相等（或差在 1% 内） |
| 对象框 vs 画布 | 相等（超过版心时才等比缩，且这种情况要单独记录） |
| 双击 | 框不变大、不留白、不裁切 |
| 走线与端点 | 重存后端点仍落在连接点上（用 `temp/工具/端点落点规则.cjs` 那套复核） |
| 相对位置 | 节点间距与改画布前一致（只平移的验证） |
| 残留 | 无 VISIO.EXE 残留 |

## 7. 与 11 号的关系

两条路线**共用同一条尺寸链**（画布 → 框 = 画布 × scale；预览件 → 声明；Word 把声明映射到框），差异只有两处：

1. **预览件来源**：Visio 真图 vs 我们自产；
2. **画布是否可信**：走 Visio 时画布应被修正为真实绘图范围（本文第 4 节），无 Visio 时保留那 10% 余量的妥协。
