# 12-Visio路线与无Visio路线的差异（"改画布"方案）

> 用途：**区分"无 Visio 嵌入"与"有 Visio 嵌入"的结果差异**，并记录"走 Visio 时修正画布大小"这一步的目的、依据、实测数据与实现。
> 前置：11 号（非 Visio 路线的尺寸换算与参数说明）、10 号（Visio COM 归一化的调用与口径）。
> 状态：**已实现**（`scripts/visio-normalize.ps1` 的"修正画布"一段），真实工程实测通过。

## 1. 一句话差异

| 路线 | 画布（页面）是什么 | 预览件是什么 | 结果 |
| --- | --- | --- | --- |
| **无 Visio** | 生产端生成时留了约 10% 余量的页面 | 我们自产的示意 EMF（"虚线框 + 题注"） | 画布、件、框三者由我们的公式串起来；算不出走线，极端情况下连线会落在画布外——**这些都可接受** |
| **有 Visio** | 修正为 Visio 的真实绘图范围（含走线、余量 0） | Visio 渲染的**真图** EMF | 件覆盖的就是画布本身；页面去掉余量后更多图能"不缩放"放进版心 ⇒ 双击时框不再被恢复成更大的尺寸 |

**10% 余量、自动连线、连线偶发越界，都是"无 Visio 路线"的妥协产物**：上游 mmd2vsdx **完全不依赖 Visio，且被禁止调用任何 Visio 接口**，所以它给出的画布不是真值、只是接近。有了 Visio，绘图范围才有真值（`Page.Export` 的边界包含走线），这个范围可以直接用。

## 2. 目标与限制

目标：走 Visio 时 **画布 = Visio 的真实绘图范围**，于是

```
页面 = 绘图范围（余量 0）  ⇒  件声明 = 页面（同一张图的范围）
                          ⇒  框 = 画布（不被版心限缩时）⇒ 初始与双击一致
```

限制（用户口径）：

1. 不加节点、不改文档内容；
2. 不改 Visio 输出件（EMF）的字节；
3. 只用 Visio 官方接口；
4. 不留 Visio 进程、不阻塞、不卡死；
5. 无 Visio 路线保持现状（它的妥协是可接受的，不再投入）。

## 3. 实测数据（本机，2026-09-29）

样本：`05-flowchart-1.vsdx`（mmd2vsdx 产物）。

| 量 | 值 |
| --- | --- |
| 页面（原始） | 1.6606 × 3.1731 in |
| 节点包围盒 | 1.5000 × 2.8750 in（正好是页面的 90%，即那 10% 余量） |
| Visio 的绘图范围 `BoundingBox(3)` | 0.0803,0.1491 .. 1.5803,3.0241 in（1.5000 × 2.8750 in） |
| 改画布后 | 页面 1.5000 × 2.8750 in，内容恰好落在页内（bbox 归零），**相对位置不变** |
| Visio 导出件的声明尺寸 | 0.9815 × 1.8516 in（**页面 ÷ 1.53~1.55**） |

关于最后一行：`PageScale` / `DrawingScale` 都是 1:1，也没有 `PrintScale` / `PrintFitOnPages` 单元格，所以这不是打印缩放。**它不影响显示**：Word 是按"件声明 → 对象框"映射的（非 Visio 路线一直如此），只要框 = 画布，预览就会铺满框。因此判定"件声明 = 页面尺寸"这个目标**不必追求**。

接口行为（同一批实测）：

| 调用 | 观察 |
| --- | --- |
| `Page.BoundingBox(3, [ref]…)` | 可用，给出绘图范围（页面坐标，英寸） |
| `PageSheet` 的 `PageWidth/PageHeight` 赋值 | 生效 ⇒ **改画布可行** |
| 逐个形状解锁 `LockMoveX/LockMoveY` 后写 `PinX/PinY` | 节点可平移；**动态连线写不动**（位置由端点驱动，跟着节点走即可，失败属预期） |
| `Page.ResizeToFitContents()` | 只会把页面**撑大**（自加约 0.175in/边），导出仍是绘图范围 ⇒ 不用 |
| `Page.CenterDrawing()` | 会把内容推出页面（某节点 y = −0.32in，将被裁）⇒ 不用 |

## 4. 实现（`scripts/visio-normalize.ps1`）

`OpenEx` 之后、`SaveAs` 之前插入一段，逐张执行：

```
1) bbox := Page.BoundingBox(3)（取不到退到 BoundingBox(2)；都取不到就跳过修正、照原流程走）
2) 页面尺寸 := bbox 尺寸（余量 0）
3) 逐个形状：解锁 LockMoveX/LockMoveY → PinX/PinY 减去 bbox 原点（只平移不缩放）
4) 继续原来的 SaveAs（重存 vsdx，页面已是修正后的真值）→ Export（真图 EMF）
```

安全网：整段在原有的逐张 try/catch 里，任何一步失败只是"这张没修正画布"，照样出图；整批起不来仍走原回退。

## 5. 实测收益与剩余限制（真实工程 23 图）

| 指标 | 结果 |
| --- | --- |
| 图块 / 警告 | 23/23 嵌入、0 失败、0 警告 |
| 页面是否已去余量 | 是（例：#2 从 5.16×8.31in → 4.68×7.54in = 绘图范围） |
| 框 = 画布（双击不变） | **14 / 23** |
| 仍被限缩 | 9 / 23，原因是**画布本身就比版心宽**（6.6~26.8in 对版心 6.36in），与余量无关 |
| 临界样本 | #3（476pt，超版心 4%）、#16/#19（493~495pt，超 8%）——若版心宽 40~50pt 或这些图的画布能收得更紧，也能进入"不缩放" |

**剩余限制**：画布宽于版心的图，双击后框仍会被恢复成页面自然尺寸（因为编辑态按页面显示，而我们无法让一个超栏宽的对象既"缩进栏内"又"等于页面"）。要消除它们只能改生产端（页面尺寸 ≤ 版心），这超出 documentor 的范围。

## 6. 已否掉的路

| 方案 | 为什么否掉 |
| --- | --- |
| 改 Visio 件的字节（声明矩形 / 设备 dpi / 逻辑 dpi） | 深度干预别人的产物；实测分别导致"框被撑大"与"内容与声明对不上、靠左上留白" |
| 往页面里加整页白底形状，让导出覆盖整页 | 等于加节点、改内容，用户明确不允许 |
| `Page.ResizeToFitContents()` / `Page.CenterDrawing()` | 见第 3 节的实测 |
| 对象框按"件"的尺寸定 | 初始框小于页面 ⇒ 双击后变大（就是本次要修的现象） |
| 对象框按"画布"定、件拉伸填满 | 现在的做法；件与页面比例若不一致会轻微形变（实测两轴差 ≤13%，仅 #5 一类） |

## 8. 与 11 号的关系

两条路线**共用同一条尺寸链**（画布 → 框 = 画布 × scale；预览件 → 声明；Word 把声明映射到框），差异只有两处：

1. **预览件来源**：Visio 真图 vs 我们自产；
2. **画布是否可信**：走 Visio 时画布被修正为真实绘图范围（本文第 4 节），无 Visio 时保留那 10% 余量的妥协。
