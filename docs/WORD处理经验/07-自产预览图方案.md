# 07 自产预览图方案（预览图归 documentor）

> 决策：**mmd2vsdx 只产出 vsdx**；预览图是 Word 嵌入才需要的东西，且与对象框/画布强相关，
> 因此**归 documentor**。策略是：**没有预览图就自产一张，且不能纯空白——要带示意性文字**。
> 本文是实施前的规划，配套的实测结论见 06 号。

## 1. 范围

**做**：documentor 在嵌入时，对"没有预览图"的图形自产一张带文字的预览件；对"有预览图"的做自洽校验与必要修正。

**不做**：改 mmd2vsdx 的接口与产出；带真实渲染画面的预览（将来若要，走"生成侧可选提供"的通道，见 06 号分工表）。

## 2. 必须遵守的已知约束（06 号实测）

1. 结构最小件 = 文件头 88 字节 + 第 1 条 EMF+ 头注释 44 字节；画面可有可无；
2. **自洽式**：`声明尺寸 = 画布 × (LogicalDpi ÷ 参考设备dpi)`；参考设备与 `LogicalDpi` 取任一组自洽值即可；
3. **护栏**：声明尺寸**不得等于**对象框尺寸（相等必被 Word 撑大）；
4. 必须保留：`rclFrame`、`nHandles = 3`、`szlDevice`/`szlMillimeters`、`LogicalDpi`、第 1 条 EMF+ 头记录；
   可删/清零：尾部 20 字节、结束记录、全部绘制记录、其余 EMF+ 注释、`rclBounds` 内容、图形版本、`EmfPlusFlags`；
5. 画面内容与"框变不变"无关（空白件、带画面件都实测通过）；
6. **双格式件的画面正本在 EMF+ 层**：若 EMF+ 层为空、只写 GDI 记录，EMF+ 感知的渲染器可能什么都不画
   ⇒ 带文字的件必须两层一致，或由渲染器一次产出。

## 3. 设计

### 3.1 输入优先级

| 情况 | 处理 |
| --- | --- |
| `figures[k].preview` 有，且自洽式成立、声明 ≠ 框 | 原样使用 |
| 有，但声明尺寸不自洽 | **保留其画面**，只改三个尺寸字段使其自洽后使用；记 `warnings` |
| 没有 | **自产一张带文字的件** |

### 3.2 自产件的形态（两种，先落 B）

**A. 手写 132 字节 + 追加 GDI 文字记录**
优点：不依赖任何资源。缺点：EMF+ 层为空，文字可能不显示（约束 6），需人验。

**B. 内置"带文字模板 EMF" + 运行时只改尺寸字段（推荐）**
- 模板在**构建期**用 .NET GDI+ 生成一次（`EmfPlusDual`：画边框 + 居中文字），两层内容齐全 ⇒ 文字一定显示；
- 模板随包发布（`packages/postprocess/resources/preview-template.emf`），运行时**不需要任何渲染器**；
- 运行时只改这三处，使文件自洽：
  1. `rclFrame` = 画布 × (LogicalDpi ÷ 参考dpi)；
  2. 参考设备（`szlDevice`/`szlMillimeters`）与 `LogicalDpi` 用模板自带的固定自洽组，不随机器变；
  3. 若只是改字段值（长度不变），`nBytes`/`nRecords` 无需改动。

**模板文案**（先固定，后续可配置）：

```

双击可用 Visio 查看 / 编辑
```

### 3.3 代码落点

| 位置 | 改动 |
| --- | --- |
| `packages/postprocess/src/preview.ts`（新增） | `makePreviewEmf({ canvasWIn, canvasHIn })`：读模板 → 改字段 → 返回；`isPreviewConsistent(emf, canvasWIn, canvasHIn)`：自洽校验；`assertNotFrame(declaredIn, frameIn)`：护栏 |
| `packages/postprocess/src/embed.ts` | 无 preview 时调用自产；写入前跑护栏与自洽校验；**防御性剥掉** vsdx 里的 `docProps/thumbnail.emf`（连同 `_rels/.rels` 关系与 `[Content_Types].xml` 声明） |
| `packages/docx/src/figure-export.ts` | 把上游给的预览件**透传**到嵌入那一步（现在这条链路是丢掉的） |
| `packages/postprocess/resources/preview-template.emf` | 模板资源（构建期生成，产物入库） |
| `packages/postprocess/scripts/make-preview-template.ps1` | 生成模板的一次性脚本（入库，便于将来重做模板） |

### 3.4 降级与日志

- 模板缺失或解析失败 ⇒ 退回 A（132 字节手写件，无文字），记 `warnings`；
- 自洽校验失败 ⇒ 修正后嵌入，记 `warnings`；
- 剥缩略图失败 ⇒ 记 `warnings`，不中断。

### 3.5 判定标准（人工）

双击对象 → 关闭 Visio → 保存 → 重开，量 `<v:shape style>`：

- 合格：框变化 ≤ 0.5%（实测合格件 405.30 → 406.30pt）；
- **不合格**：变成画布尺寸（如 869.65 × 634.40pt）或几百/上千英寸。

## 4. 实施步骤

1. 写模板生成脚本，产出带文字的 `preview-template.emf`，并**先出实例人验一次**（验证"带文字 + 自洽式"这条路成立）；
2. 新增 `preview.ts`（合成 + 自洽校验 + 护栏）；
3. `embed.ts` 接入：无预览即自产；剥 vsdx 缩略图；写入前护栏；
4. `figure-export.ts` 透传预览件；
5. 单测：结构（88+44 或模板结构）、自洽式、声明 ≠ 框、`nBytes`/`nRecords` 正确、无预览/有预览两条路径；
6. 文档：06 号增补"自产件形态"，README 行更新；
7. 人验：出一份 4 对象的实例，双击保存后量框。

## 5. 验收标准

1. 不传预览 ⇒ 文档里能**看到带文字的预览**，双击保存后框不变（≤0.5%）；
2. 传了自洽的预览 ⇒ 原样使用；不自洽 ⇒ 自动修正后使用，框同样不变；
3. 单测覆盖第 4 步列出的断言；
4. 嵌入产物里不含 vsdx 的 `docProps/thumbnail.emf`。

## 7. 实施记录（2026-09-24）

**已落地**（分支 `feature/自产预览图`）：

| 项 | 结果 |
| --- | --- |
| 模板 | `packages/postprocess/resources/preview-template.emf`（2560B，67 条记录，浅灰边框 + 两行提示文字，画面两层齐全）；由 `packages/postprocess/scripts/make-preview-template.ps1` 生成，可重建 |
| 模板 dpi 组 | 参考设备 1920×1080px / 508×286mm（**96dpi**）+ `LogicalDpi` **120** ⇒ 比值 1.25 ≠ 1（规避"声明 = 框"） |
| 内联 | 模板以 base64 常量内联在 `packages/postprocess/src/preview-template.ts`，避免打包漏带资源 |
| 合成/校验 | 新增 `packages/postprocess/src/preview.ts`：`makePreviewEmf`、`normalizePreviewEmf`、`readPreviewMetrics`、`checkPreviewConsistency`、`expectedDeclaredIn`、`declaredEqualsFrame` |
| 接入 | `embed.ts`：无预览即自产；有 EMF 预览则只校正声明尺寸；护栏（声明 = 框）记 `warnings`；读不出画布尺寸也会报警 |
| vsdx 侧 | `stripVsdxThumbnail` 剥掉 `docProps/thumbnail.emf`（部件 + 关系 + 内容类型），嵌入前调用 |
| 透传通道 | `FigureConvertResult.previewBase64?`（上游可选给 EMF），`figure-export.ts` 透传 |
| 单测 | `localscripts/tests/preview.test.ts`（6 条）+ 既有套件；`pnpm test:local` 326 通过、`pnpm typecheck` 无错 |

**顺带修掉的真 bug**：`vsdx.ts` 的 cell 解析只认 `N="…" V="…"` 这种双引号且固定顺序的写法，
而 mmd2vsdx 产出的 page XML 用**单引号**、属性顺序也不固定 ⇒ 画布尺寸静默读不到，
对象框与预览尺寸全部退化到兜底值（6 × 4.5in）。现已改为**引号风格与属性顺序都不敏感**，
并把改写统一成双引号；本地套件里三条相关红测试随之变绿。

**按新口径更新的本地测试**（原期望是旧行为，非产品回归）：

1. `figure-export.test.ts`「不提供预览…没有 v:imagedata」→ 改为断言"自产带文字预览件"；
2. `embed.test.ts` 传入不可解析的 3 字节"EMF"→ 改为传入真实模板件（不可解析会被报警）；
3. `embed.test.ts` 的两处页面尺寸期望：原来写"源 vsdx 原样"，与 `patchPageSize` 默认开启的实际口径相反 → 按"页面被改成内容包围盒"更新。

**尚未做**：人工双击验收（本方案第 7 步）——出实例 → 双击 → 关 Visio → 保存 → 量框（合格抖动 ≤0.5%）。

## 7.5 收口口径（2026-09-28 定型，人工验收通过）

五轮人验把口径逼到了下面这一版，**这五条是硬约束，改动前先读**：

| 约束 | 内容 | 依据 |
| --- | --- | --- |
| dpi 必须是常规值，且**两轴严格一致** | 参考设备固定 **144dpi**（写成 `1440×1440px / 254×254mm`，两轴都严格 144.00）、`LogicalDpi` 固定 **120**；护栏 `previewDpiOutOfBand` 卡区间 [96,160] 与两轴一致性 | 三次踩坑：按对象压到 64~87 ⇒ 框被放大；按分轴取「画面像素 ÷ 画布in」在扁图上算出 **57 / 600 / 1992** ⇒ 同样放大；参考设备写 `1440×1080/254×191mm` ⇒ 横轴 144.0、纵轴 143.6 ⇒ 纵轴声明与参考对不上（0.27%） |
| 声明尺寸只认自洽式 | `rclFrame` = 画布 × (LogicalDpi ÷ 参考dpi)，两轴同一比例 | 自洽式成立时帧不移动（T1a/A5/B2/C2/D1–D3 七组样本）；统一 120/144 ⇒ 声明 = 画布 × 0.833 |
| **画面内容的物理尺寸 = 声明尺寸** | 画面像素 = **画布in × 逻辑dpi** ⇒ 内容物理尺寸 = 画布 × L ÷ 参考dpi = 声明尺寸（实测比 1.000 ±0.3%） | 消费端是把**声明矩形**映射到对象框上的：内容只有声明的 28% 时，就只占框一角（"没铺满/偏左上"✗）；比值反过来就"只有一部分/偏右下"✗ —— 四种现象同一个根因 |
| 声明 ≠ 对象框 | 相差 ≥5%（撞上时整体挪 10%：108/120） | 相等时必然被撑大（T1b 样本） |
| 内嵌 vsdx 页面不动 | `patchPageSize` 默认 false | `pages.xml` 是生成侧给的权威画布；按包围盒压小会缩框并把内容挤到页面外 |

**画面按对象算，没有模板**：画面像素、内缩（框短边 ×12%）、线宽（×0.8%）、字号（×5.5%，按整行不超内框收窄）
全部由算式给出；文字步进必须用**实测表**（`ADVANCE_EM`，Microsoft YaHei：`m`=1.25em、汉字=1.3333em），
按 0.55em 估会让英文叠字 ✗。墨迹外接写进 `rclBounds`，保证 ⊂ 画面。

**边界（不越界）**：画布尺寸与比例**由生产端给定，是什么样就是什么样** ✓；本侧只保证
"内容 = 声明（⇒ 铺满不裁）+ 帧不移动"两件事。

**实测**（经典四图 + 真实工程 23 图）：内容 ÷ 声明 = **1.000**（±0.3%）、`LogicalDpi` 全部 **120/120**、
参考 dpi **144.0/144.0**、越界 0/23、护栏"声明 ≈ 框" 0 撞、警告 0、预览件 23/23 可解析、连线 23/23；
本地套件 327 通过、typecheck 无错。

**走过的死路（别再走）**：

1. **把 dpi 当自由变量去凑铺满**（无论按对象改、还是按分轴算）⇒ 帧被撑大（原因见上表第 1 条）；
2. **靠预生成模板档位近似比例与尺寸** ⇒ 2 倍步长最坏只铺满 0.59、比例也对不上（画面 15.97 vs 框 20.90 ✗）⇒ 已删除整套模板，改按对象算；
3. **手写 EXTTEXTOUTW 时用估的步进宽度** ⇒ 英文叠字（见上表外的实测表说明）。

**另一处口径变更**：`patchPageSize` 默认 **false**（`pages.xml` 的页面尺寸是生成侧给的权威画布）。
开着它时，内容包围盒只由"四格齐全"的形状算得，77 个形状的图纸被算成其中一个形状的大小，
页面从 8.896×10.209in 被压到 2.559×1.804in ⇒ class 对象框缩水到 184×130pt，图纸内容还会落到页面外。

## 8. 风险与未证事项

1. "带文字模板 + 运行时改尺寸"**尚未实测**——本方案第 1 步就是出实例人验；
2. EMF+ 层与 GDI 层内容不一致时的渲染表现未测（模板走两层一致，规避该风险）；
3. 跨 Word 版本、跨 Office 位数未验；
4. 模板的固定 dpi 组是否在所有机器上都相消——06 号推导为"相消"，但只在单机三组上验过；
5. 文案是否需要按"无 Visio 环境"分场景给不同提示，待定。
