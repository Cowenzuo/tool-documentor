# 表格与合并

> 本页说明表格怎么组 XML、纵向合并怎么写、合并判定按什么规则。表格是从零生成的，
> 不像正文那样依赖骨架，所以这里的元素顺序要自己保证。

## 1. 表格骨架

```xml
<w:tbl>
  <w:tblPr>宽度、边框、单元格边距</w:tblPr>
  <w:tblGrid><w:gridCol w:w="3024"/>…</w:tblGrid>
  <w:tr><w:tc><w:tcPr><w:tcW …/></w:tcPr><w:p>…</w:p></w:tc>…</w:tr>
</w:tbl>
```

- `w:tblGrid` 的列数与各列宽度决定布局，缺列会让 Word 自行补列；
- 每列宽度按正文宽度均分，正文宽度取 9072 缇；
- 边框分内外两档：外框给 8 分之一磅，内线给 4 分之一磅，这是三线表的常用比例；
- 单元格边距左右各留 108 缇，文字不贴边。

**行数与列数以 `data` 的实际形状为准**，`rows` / `cols` 只是提示性元数据：

- `rows` **不含表头**（`headers` 是独立的一行）；
- `rows` 允许与 `data.length` 不等——写入侧可能按"数据行 + 表头"的旧口径给值。
  因此渲染与导出**都不拿 `rows` 当上界**：早先取 `min(rows, data.length)`，
  在 `rows < data.length` 时会静默丢掉行尾数据（85 行的表写成 50 行就丢 35 行）；
  现在逐行走 `data`，一行不多一行不少；
- `cols` 也不当上界。列数取"表头长度、每行实际长度、`cols`"里的最大值：
  模板与实例 JSON 不给 `cols` 时它是 0，早期实现按 `max(1, cols)` 算列数，
  一张 3 列的表会导出成 1 列，右边几列静默消失，与 `rows` 那条是同一类缺陷；
- 行比列短时按列数补空格，一行写满 `w:tblGrid` 的列数。缺格的表格行会让 Word
  自行补列并错开边框与合并；
- 形状校验在写入侧做（core 的 `checkTableShape`）：列数不一致直接拒绝写入并说明位置，
  `rows` 不一致只提示。以前没有这道校验，问题要等导出时被 `min` 掩盖过去。

依据：规范加实测。85 行表在 `rows=50` 下丢 35 行、4 列表在 `cols=0` 下丢 3 列，
两条都已复现并修复，单测钉住。

## 2. 单元格属性的顺序

`w:tcPr` 的子元素顺序同样是规范强制的。合并相关的片段顺序是：

```
w:tcW → w:vMerge → w:vAlign
```

顺序错了，Word 会把合并标记当不存在，合并静默失效。这一点在实测确认过：
`w:vMerge` 排在 `w:tcW` 之前时表格看起来是散的。

依据：规范加实测。

## 3. 纵向合并

合并的写法是起点格加 `restart`，后续格留空并标记续格：

```xml
<w:tc><w:tcPr><w:tcW …/><w:vMerge w:val="restart"/><w:vAlign w:val="center"/></w:tcPr>
  <w:p>合并后的内容，只出现这一次</w:p></w:tc>

<w:tc><w:tcPr><w:tcW …/><w:vMerge/></w:tcPr><w:p/></w:tc>
```

- 起点格加 `w:vAlign` 让内容垂直居中，长格看起来才正；
- 续格必须是空段。内容重复出现会让 Word 显示两遍；
- 表头行不参与合并；
- **这里的"续格留空"只是 XML 的写法**，工程数据里那一格的值不受影响——
  数据用 `rowSpans` 记住跨行，导出时才摊成 restart/续格（见第 4 节）。

依据：实测。Word 回读首表为 10 行 3 列 25 个单元格，起点格跨 3 行与 4 行各一处，
唯一值不合并。

## 4. 合并判定规则

判定要三处一致：编辑区的提示、预览的跨行、导出的合并。规则只有一份，放在 core 的
`resolveTableMerges` 里。两种来源**取并集**，不是二选一：

1. **显式跨度**逐格优先。表格块带 `rowSpans`，形如 `{ 列号: [[起始行, 跨几行], ...] }`，
   行号按 `data` 下标、不含表头。它**不看内容**，值可以照常保留，取消合并即可恢复原状。
   越界与重叠的跨度会被夹到可用范围内或丢弃，不产出非法合并；同一格被两个跨度重复
   认领时只认先到的那个。跨度占住的格子随即被认领，第 2 条不再碰它。
2. **兼容判定**补上没被认领的部分。`mergeVertical: true` 时按两种形态合并，表头行不参与：
   - **连续相同**：连续若干行 trim 后非空且完全相同，合成一格；
   - **空串向上合并**：非空值后面跟的**连续空串**并入上面那一格，"留空 = 续格"的写法
     就是这个形态，组延续到下一个非空值为止。
   列首的空串没有可并入的对象，跳过，不把开头整片空白并成一格。

旧口径是"有 `rowSpans` 就整体接管"，一张表只要带了不完整的跨度，其余该合的地方就静默
不合了。现在两种来源取并集，各管一段：显式跨度认领过的格子，兼容判定不再碰；其余该合的
地方照合。

界面上不再有"把判定结果写成显式跨度"的第二次操作。合并由勾选框直接决定：勾上按上面的规则
合并，取消就散开，单元格内容始终留在原处，所以这一步是可逆的，撤销即可退回。`rowSpans`
因此只由接手外部数据时带上，程序不主动写它；缩表时仍会按新尺寸裁剪既有跨度，免得越界的
跨度落到表外。

**列数口径**三处同样要一致。列数取表头长度、提示性 `cols` 与各数据行长度的最大值，
至少 1 列；没有数据行时按 0 行返回空网格，不凭空造出合并。判定侧原先只取
`Math.max(...data.map((r) => r.length))`，既不算表头也不算 `cols`，于是"表头 3 列、
数据行 2 列"的表中，定义在第 3 列的 `rowSpans` 会被 `c >= cols` 当成越界丢掉，
预览与导出都少一处合并。导出侧 writer 一直是三者取最大值，那次修复就是把判定拉到
同一口径。`TableSpanSource` 因此多了可选的 `headers` 与 `cols`，不传时仍按数据行宽度算，
老调用方的行为不变。

> 两种判定并存的原因：`rowSpans` 把跨行写进数据，与内容彻底解耦，是想怎么填都成立的正道；
> 兼容判定则是为了让**既有工程的"留空"写法立刻能用**，不必等迁移。
> 二者取并集，各管一段，互不抢格子。

依据：单测覆盖显式跨度、兼容两形态、并集语义、越界与重叠、列数口径与缩表裁剪；docx 端到端单测钉住"表头 3 列、数据行 2 列"的第 3 列不再丢合并；
真实工程实测 46 张表新规则判定 151 组合并，产物 `vMerge restart=151 / 续格=561` 与判定逐一对齐。

## 5. 判定逻辑为什么放 core

同一个判定要被三处消费，放三份实现迟早会走偏。core 里导出纯函数
`resolveTableMerges`，返回与数据同形状的矩阵，起点格给出跨行数，被覆盖格标记出来，
谁用谁取自己需要的字段。

渲染进程从子路径导入这个函数，不从包根导入：包根还挂着 SQLite 存储，
浏览器端不需要也不该拉进来。

依据：实测。预览、编辑区与导出用的是同一个函数，46 张表的合并处数完全一致。
