# 项目特定规范（Documentor 重写版）

> 只在 tool-rwdoc 仓库成立的约定。通用规范见同目录
> [提交规范.md](提交规范.md)、[代码规范.md](代码规范.md)、[文档规范.md](文档规范.md)。
> 条文里出现"本项目"的地方，都指这个把结构化文档树写成 DOCX 的
> Node 与 Electron 工程，也就是 Documentor 的 Node 重写版。

## 1. 支持范围

- 文档格式不内置：任何能用 docx 格式化的规范文档都由「结构模板 + 样式模板」驱动，
  模板由用户从外部目录提供，软件只提供处理管线；
- 内容块支持八类：文本、图片、表格、公式、代码、流程图、有序列表、无序列表。
  其中图片块真正嵌入 DOCX，表格支持同列纵向合并，流程图走上游转换后按对象嵌入；
- 导出能力缺省可用：没有流程图块时导出照常完成，流程图的转换能力缺失时按文本导出，
  不中断交付；
- 唯一事实源是 `docs/WORD解压结构研究/`。实现与验收对着它，不对着历史产物。

## 2. 仓库结构

```
packages/*/          本工程的全部模块，平级放在这里：
                       core / templates / docx / postprocess 是纯逻辑库，
                       desktop 是可执行程序（Electron 壳，含 main / preload / renderer）
samples/             demo 级实例：示例模板与样例工程，供直接打开测试，无外部版权内容
scripts/             入库的辅助脚本：上游契约检查、产物校验、按需构建库、一键启动
localscripts/        本机脚本，不入库：单测、E2E 探针、Word 核对脚本、开发工具
release/             打包产物，不入库；`pnpm package` 出安装包，`package:dir` 出免安装目录
temp/                开发期草稿与临时产物，不入库，可随时清空
docs/                文档，各区职责见第 8 节
```

`localscripts/` 与 `scripts/` 都不是程序的一部分：

- `localscripts/` 是纯本机辅助——单测、探针、核对、开发工具。**任何时候整目录删除，
  程序的功能、构建产物与验收结论都不受影响**；它不入库，也不接受提交；
- `scripts/` 只服务开发、构建与打包的便利，同样可以整目录删掉；删掉只影响开发工作流的
  便捷性，不影响已构建的程序与它产出的文件；
- 由此定死一条：**产品能力不得落在脚本里**。模板校验与必需键推导、锁的判定与写入拒绝、
  模板加载、序列化与 OOXML 打包，全部在 `packages/` 内实现，并且只靠类型检查、构建与
  打包产物就能验证；
- 依赖方向是**脚本可以引用产品代码，产品代码不得引用脚本**。`package.json` 里
  `build`、`typecheck`、`verify` 三条链不得依赖 `localscripts/`。

`packages/` 下的模块只是**角色不同，同属一个工程**，不再用 `apps/` 分组：

- 依赖方向只允许 **可执行 → 库**，以及库之间 `core ← templates ← docx`；
  **任何库都不得依赖 desktop**（否则打包与单测都会被 Electron 绑住）；
- 这条边界让四个库能脱离 React 与 Electron 单独构建、单独单测（库包自身的 devDeps
  只有 `@types/node`，vitest 挂在仓库根）；
- 要做可独立发布的 CLI 时，同理在 `packages/` 下加一个包即可。

模板不在本仓库：真身在仓库外的同级目录 `../tool-documentor-template/`，由另一个仓库单独管理，
也与 `link:../../../tool-mmd2vsdx` 一样属于仓库外依赖。**模板目录指的是那个仓库的 `packages/`
子目录**（`structures/` 与 `styles/` 平级放在那里），不是仓库根——
配错一层，软件会静默跳过整个目录，界面上就是一片空白。

模板目录里没有清单文件：每份模板的身份是 JSON 里的 `uuid`，目录名与文件名都用它，
名字（`cn` 主名、`en` 副名）只作展示。旧格式（目录名不是 uuid、带 `manifest.json`）不并存，
由模板编辑界面的迁移动作改成新格式。

`packages/` 四个包职责单一，依赖方向固定：

| 包 | 职责 | 依赖 |
| --- | --- | --- |
| `core` | 文档树与内容块模型、SQLite 工程存储 | 无 |
| `templates` | 模板注册、结构模板实例化、样式键推导 | `core` |
| `docx` | 序列化、OOXML 打包、图与对象嵌入编排 | `core`、`templates` |
| `postprocess` | OLE 复合容器、VSDX 装配、对象段替换 | 无 |
| `desktop` | Electron 壳与界面：main 持工程与导出管线，preload 只做类型化桥，renderer 是 React 界面 | 上面四个 |

`desktop` 三端共享 `src/shared/` 里的 IPC 契约。它是**唯一依赖 electron 与 UI 库的模块**，
其余四个包保持零 UI 依赖。

## 3. 构建与运行

```bash
pnpm install
pnpm dev            # electron-vite dev，渲染层热更新
pnpm typecheck      # 全仓类型检查
pnpm build          # 先构建四个库包，再打桌面壳到 packages/desktop/out/
pnpm verify         # 门禁：类型检查、构建，收尾再跑上游契约检查（只报告，不阻断；不跑测试）
pnpm verify:upstream # 上游契约检查的严格模式，漂移即以退出码 1 拦住（发布前用）
pnpm test:local     # 本机单测：源码在 localscripts/tests/，不入库
pnpm check:locks    # 权限自检：模板里写的锁，工程侧拦不拦得住（脚本在 localscripts/，不入库）
pnpm check:styles   # 样式模板编辑自检：读、写回、导入、改名、删除、试跑、迁移（同上，不入库）
pnpm check:ui       # 界面自检：起真实 Electron 点一遍模板编辑，物理点击 + 落盘校验（同上，不入库）
```

应用的启停由用户掌握：**用户自己关掉开发版就是不要它跑，不要替他重启**，也不要因为
退出码非 0 就当成出错——正常关窗也是这个码。要分辨退出原因看主进程打的
`[lifecycle]` 日志：有「渲染层请求关闭窗口」就是点了标题栏的 ✕，属正常操作；
只有「窗口收到关闭请求」才是系统关的；「渲染进程结束」「子进程结束」才是异常。

打包与产物校验：

```bash
pnpm package:dir    # 免安装目录 release/win-unpacked
pnpm package        # NSIS 安装包
node scripts/verify-package.cjs   # 校验 asar 内容与分发边界
```

与通用规范的偏差，按下面执行：

- 脚本用 `*.cjs`。入库脚本要 `require` 构建产物，CommonJS 更直接；
  纯 ESM 且不需要 require 的脚本才用 `*.mjs`；
- `tsconfig.base.json` 开了 `strict`、`noUncheckedIndexedAccess`、
  `noFallthroughCasesInSwitch`。未使用变量编译期不拦截，靠自查与评审把关；
- 注释以中文为主，内部诊断日志带模块前缀，如 `[templates]`、`[renderer:csp]`；
- 本项目有 React 与 CSS 面，通用篇里省略的前端条目按现有代码风格办。

## 4. 产物与命名

- 导出产物就是用户给的那个路径，不再附加后缀；中间态只在导出过程内部存在，
  收尾时清掉；
- 工程目录固定在 `documentor.dproj` 所在目录，库文件 `documentor.db`，
  图片落在工程内 `images/`，一律用相对路径引用；
- `release/` 是本地产物目录，不入库；`samples/` 里的样例工程与合成模板入库；
- **`release/` 里的成品不随开发提交重建**。开发期只做源码、构建产物与门禁验证，
  重新打包是用户明确要求的动作，那时才动 `release/`，理由是它是用户当前在用软件；
- 同一输入两次导出结果一致。若产物出现无谓差异，先查列表编号克隆的随机值。

## 5. 验收口径

- 主验收是全仓类型检查、构建与打包产物校验，也就是 `pnpm verify` 那一条链；它不跑测试，
  也不依赖 `localscripts/`。
- **一个能力范畴一份自检，改哪块跑哪块。** 能力与自检一一对应、互不牵连，哪一份红了就说明
  哪个能力有问题。改了某个能力就只跑它那一份，顺手带上几秒钟的 `pnpm typecheck`；
  `pnpm verify` 留到合并与定版这种节点。不把各份自检拧成一个全量大套件，也不为一次小改动
  跑整套验收。
- 现有的能力自检都在 `localscripts/`，**不入库，可随时整目录删除**，删掉不影响程序与验收结论：

  | 命令 | 管哪个能力 |
  | --- | --- |
  | `pnpm check:locks` | 结构锁在工程侧的拦与放 |
  | `pnpm check:styles` | 样式模板编辑的读、写回、导入、改名、删除、试跑与迁移 |
  | `pnpm check:ui` | 模板编辑界面：起真实 Electron 点一遍，物理点击加落盘对账 |

- 新开一个能力就新开它自己的一份自检，改口径时连自检一起改；不往别人的那份里塞。
- 库包的单测只覆盖 `src`：包的 `exports` 把 `import` 指到 `src/*.ts`、`require` 指到
  `dist/*.js`，vitest 走的是前者，`dist` 一侧没有等价的自动校验。改动 `exports`、
  `tsconfig.build.json` 或产物目录之后，要构建一次，并在 `require` 路径上手工验一遍
  自己改的那个入口，别只看绿灯；
- 产物验收一律用 Word 回读，不只看 XML。核对项见
  `docs/WORD处理经验/01-Word实测核对方法.md`；核对脚本在本机
  `localscripts/word-checks/`，同样不入库；
- 界面改动要在构建后的应用里实测：`pnpm check:ui` 拉起真实 Electron，点一遍主流程，
  断言落在磁盘上，失败留截图；
- 撤销与重做的口径见 `docs/版本开发过程/PLAN-10-撤销与重做方案.md`。原来覆盖它的那条 E2E
  已随脚手架删除，这个能力现在没有自检；哪天动到它，自检一起补；
- 验证脚本的取舍见《代码规范》第 5 节：只对着外部事实，盯自家输出的脚本一律删除，不修；
- 交付前的完整门禁是 `pnpm verify`：类型检查、构建两项，收尾再跑上游契约检查。
  它**不跑测试**：单测在本机按 `pnpm test:local` 单独跑，两条口径不要混。上游检查是
  报告模式，漂移只打印不阻断；要拦住漂移用 `pnpm verify:upstream`，发布前跑。

## 6. 文档地图

| 目录或文件 | 放什么 |
| --- | --- |
| `docs/WORD解压结构研究/` | WORD 包内部结构与本工程写入方式，唯一事实源 |
| `docs/WORD处理经验/` | 踩坑与解法、核对方法；核对脚本在本机 `localscripts/word-checks/`，不入库 |
| `docs/版本开发过程/` | 各阶段方案与整改记录，历史材料，不回溯改写 |
| `docs/AI开发约定/` | 本目录 |

写文档前先判断归属：讲 WORD 包内部长什么样进结构研究，讲踩过什么坑进经验区，
讲当初为什么这么设计进版本开发过程，讲活该怎么干进本目录。
「已讨论、暂不实施」的功能立项不进仓库，由维护者在本机保存。

## 7. 本项目特有的技术红线

- 导出以样式模板的 docx 骨架为底，只重写 `document.xml` 与 `numbering.xml`，
  其余部件逐字节保留。改骨架前先想清楚会不会动到用户模板的版式；
- 题注域与样式里的多级列表编号互斥。题注段落不得同时挂 `numPr`，
  否则 Word 会按列表编号，和域里的编号打架；
- 与标题共用多级列表的题注层级会顶高标题计数，题注一律走域，不走列表；
- `ilvl` 只到 0 到 8。超范围的层级 Word 会报文件损坏；
- 图片块必须真正嵌入，不允许回退成占位文本。占位只在文件缺失时作为兜底出现；
- 图片显示尺寸按正文可用区域算（骨架 `sectPr` 的页面尺寸减页边距），**不得写死宽度**：
  铺满可用宽度并保持宽高比，同时受可用高度上限约束，低于 150 像素宽的极小图不放大。
  口径见 `docs/WORD解压结构研究/图片与对象嵌入.md` 第 2 节；
- 模板不随软件分发，上游 mmd2vsdx 也不进发行包，这是合规红线；
- 改完导出链路，必须用 Word 打开一次产物确认没有修复提示。

## 8. 分支习惯与历史整理

**一个分支只做一个任务。** 分支名说清任务，做别的任务另开分支，做完合回主干；
不把顺手改的塞进当前分支，否则分支就失去意义，回退与审阅都无从下手。
编辑侧与别的侧的任务同样分开关，不混在一条分支里。

**合回主干一律用 `--no-ff`**，主干上留一个合并节点，一眼看得出一条分支做过什么；
快进合并只挪指针，图上不留痕迹，等于白开分支。合并提交用 `merge` 类型，
标题写「并入某某分支」。

零散的工作期提交在定版前按大事件整合，让主干一笔提交对应一个完整事件。
整合属定版前动作，由用户发起，做法见
`docs/WORD处理经验/03-脚本手册.md` 的历史整理一节。
平时开发照《提交规范》一篇一提交，不改写已有历史。
