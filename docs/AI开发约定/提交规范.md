# 提交规范（通用）

> 适用：任何 git 仓库。项目专有的发布与分支习惯见同目录《项目特定规范.md》。

## 1. 提交消息格式

```
<type>: <中文摘要>

1. <要点一>
2. <要点二>
3. <要点三>
```

- 标题：`type: ` 加中文摘要，一行，动词开头，50 字以内；
- **标题不写括号注记**：版本号、里程碑编号、影响范围这类细节放进正文，
  标题只留一句话；也不要用 `[xxx]`、`【xxx】` 之类的标签；
- 正文：空一行后接**有序列表** 3 到 5 条，写关键要点，不赘述；
  没有值得列出的要点时可以省略正文；
- 正文写"改了什么、为什么"，不贴大段代码或 diff。

### 1.1 type 枚举

| type | 用途 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `refactor` | 重构，不改行为 |
| `docs` | 文档 |
| `test` | 测试 |
| `chore` | 构建、依赖、杂项 |

一个提交只落一个 type；改动跨类时按主要目的选，选不出来说明该拆成两个提交。

### 1.2 中文消息的写法

- 用 `-m` 数组分段传入，不要 heredoc：Windows 控制台按 GBK 解码，
  会把 UTF-8 中文写坏；
- 引用文件写仓库相对路径，引用结论写具体数值或提交号，不写"见上文""同前"。

## 2. 工作流习惯

- 一个逻辑变更一个提交：`fix:` 与 `feat:` 分开，即使同批完成；
- 提交前 `git status --porcelain` 确认待提交文件正好是目标文件，`git add` 指定文件；
- 工作树必须干净才算一轮完成；
- 已提出的修改走追加提交，不改写已有历史。

## 3. 版本管理

- 版本号用 SemVer 子集：`0.1.0`、`0.1.0-rc.N`；
- **集成发布不升版本号**，批次用 commit hash 或 git tag 标识；
- 定版发布由用户专门发起，是唯一升号场合；
- 候选期修缺陷同版本重发，不把 `rc.N` 当补丁计数器。
