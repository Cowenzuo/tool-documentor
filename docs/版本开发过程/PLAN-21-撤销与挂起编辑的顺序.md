# PLAN-21 撤销与挂起编辑的顺序

> 状态：已实施。这一轮修的是"刚打完字就按 Ctrl+Z"这条路上两个叠在一起的毛病，
> 顺带把撤销这份自检从"缩表撤得回来"扩到"防抖里的打字也撤得回来"。
> PLAN-10 第 4 节写了"栈上顺序要与用户看到的顺序一致：先把防抖缓冲里的编辑落定"，
> 那份意图在 2026-09-22 之前没有真正生效，以本文为准。

## 1 症状

内容块走 600ms 防抖才落库，撤销走的是应用级 Ctrl+Z（`AppContext` 捕获阶段），两条路各走各的。
最常做的一个动作——敲一句、马上按 Ctrl+Z 想收回——在实机上表现为：

| 走法 | 修前 | 修后 |
| --- | --- | --- |
| 打完字**立刻**按 Ctrl+Z | 界面上字还在，撤销把上一步吃掉了 | 这次打字被撤销 |
| 再等 1.5 秒 / 3 秒 | 那次打字自己写回来，栈里还多出一步 | 不会回来 |
| 打完等 900ms（已落库）再按 Ctrl+Z | 正常 | 正常 |

修前的实机读数（`localscripts/e2e/probe-undo.cjs` A 组）：
界面上是"打完立刻撤销"，历史面板里躺着一步"修改内容"，切走再切回来就变回原句，库里也是原句。

## 2 两个毛病

**其一：`flushAll` 没有真的等。** `AppContext.runHistory` 里本来就写着"先把防抖缓冲里的编辑落定"，
也确实 `await flushAll()`，但 `flushAll` 调用各页注册的 flush 时**丢掉了返回值**
（类型签的是 `() => void`），而 `NodePage.flushPending` 内部是 `void updateContentBlock(...)` 一发了之。
于是"先落定再撤销"等于没生效：撤销先跑（撤掉上一步），那次打字随后落地（自己写回去，还多一步）。

**其二：撤销之后界面那份块序列不按 store 覆盖回来。** `NodePage` 与 store 对账那段以
「store 侧的签名与上次对账一样」为跳过条件。而这一次的情况是：打字只落在本地（store 未动），
撤销把 store 退回原名，于是**签名正好回到上次对账时的那个值** —— 判定为"没变化"，跳过同步，
界面上留着那次打字。库里其实已经退回去了，切一下章节也能恢复，所以它只在"刚打完就撤销"这一瞬
看得见，最难查。

## 3 改法

| 件 | 改动 |
| --- | --- |
| `AppContext.flushAll` | 类型放到 `() => void \| Promise<void>`，逐个 `await fn()` 并 `Promise.all` 收口；注册表与 `registerFlushAll` 的签名一起放开 |
| `NodePage.flushPending` | 改成 `async`：把标题、编制说明、各内容块的写入收集起来 `await Promise.all(writes)`。调用它的地方本来就有 `await`（加块、删块、移动、换类型、保存、切节点），此前等于白等；卸载那处改成 `() => void flushPending()`，组件要走了不等结果 |
| `NodePage` 对账那段 | 跳过条件从"store 签名没变"改成"store 签名没变**且界面也还跟它一致**"（多比一份界面上那份块序列的镜像 `blocksRef`）。界面已经分叉就必须按 store 覆盖回来 |

## 4 自检

`pnpm check:undo` 从 18 项扩到 28 项，夹具仍是权限那份：

- 原有一组（表格缩容）：改列数不再弹确认、撤销按钮报得出步名、历史面板列得出这一步、
  点一次撤销后列数/表头/数据逐值回来、保存落盘也是缩表前的样子，缩完先保存也退得回来；
- 新增一组（刚打完字就撤销）三小case，每小case都**同时读界面与库**：
  A 打完立刻撤销、B 打完等 900ms 再撤销（对照）、C 打完立刻撤销并等 3 秒看会不会自己回来。
  只读界面会被"界面没跟上"骗过去，只读库会漏掉第二种毛病，所以两处都要读。

## 5 没做的

- 写入失败时界面不回滚本地那份编辑（失败会弹主进程那句原因，数值要等下次对账才回退）。
  失败本身罕见，且要修得连"哪一次写入失败了"一起记，留给以后动这块时一并处理；
- 撤销后选中项不写回 `ui_state`，重启后仍读上次保存的选中章节（PLAN-10 就记着的边界，未动）。
