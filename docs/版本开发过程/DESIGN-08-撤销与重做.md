# 撤销与重做

> 本文写撤销这条线上的当前设计：一步是什么、快照按什么粒度存、栈的上限、三个入口怎么用、
> 挂起编辑与撤销的先后顺序，以及几条已知边界。核心的一条口径是**撤销栈上的顺序必须与用户
> 看到的顺序一致**，围绕它的两处实现细节在下面第 5 节。

## 1 口径

- **撤销栈是会话级的**，跟着当前打开的工程走：不落库、不跨工程、不跨进程重启。打开、新建、
  关闭或切换工程时整栈清空，包括重做栈；
- **一步 = 一次用户可感知的编辑动作**，不是一次按键，也不是一次 IPC 往返；
- **撤销不改数据库**。改动退回内存与界面，数据库仍只在保存时全量重写。保存之后照样可以继续
  往前撤销，再保存一次就把数据库一起退回，这与 Word 的口径一致；
- **被拒绝的操作不入栈**。写入侧因为模板锁、表格形状、位置越界而抛错的写入等于没发生，
  快照也就不会留在栈上；
- **撤销与重做自身不入栈**。它们只移动栈上的位置，不产生新的一步；
- **重做栈在新编辑发生时清空**，这是撤销的常规口径。

栈的状态随每次写操作刷新：`AppContext` 在每一个变更函数成功后调 `refreshHistory()`，
把 `canUndo`、`canRedo`、最近一步的动作名与两段列表一起取回来。

## 2 什么算一步

**结构化操作一次一步，不合并**，它们各自带一个固定的步名：复制章节、裁剪章节、添加内容、
删除内容、移动内容。改动前先判断、被拒绝就不入栈，所以这些步名只有在操作真的生效时才出现。

**连续编辑按停顿合并**，三种动作各有自己的合并键与步名：

- 章节标题，键 `node:title:<节点id>`，步名「修改标题」；
- 编制说明，键 `node:desc:<节点id>`，步名「修改编制说明」；
- 内容块编辑，键 `block:update:<节点id>:<下标>`，步名「修改内容」。

合并的判据是**同一合并键加时间窗口**，两者都满足才并进上一步。窗口是 600 毫秒
（`HISTORY_COALESCE_MS`），与内容编辑的防抖窗口同值，所以「打一段字，停一下，再打一段」
是两步，「一口气打完」是一步。合并时保留最早的 `before` 与最新的 `after`，并刷新这一步的
时间戳。换对象（换了块、换了章节）自然封口，因为键变了。

`coalesceKey` 传 `null` 表示这一步不与任何步骤合并，结构化操作全部如此；不传也按 `null` 处理。

另有两条显式封口，`HistoryStack.seal()` 把上一次的键与时间清掉，下一次 `push` 一律开新的一步：

- **保存时封口**：`saveProject()` 与 `exportDocx()` 落库之后各调一次，免得撤销跨过一次保存；
- **撤销与重做时封口**：`undo()`/`redo()` 取出记录后调用，之后接着编辑不会被并到刚才那一步上。

不入栈的动作：导入图片（它只把文件复制进工程目录，不动树；换图真正落到树上的是随后的
内容块编辑，那一步自己带快照）、模板实例化新工程、设置、模板目录与界面状态。

## 3 快照按什么粒度存

快照**按受影响的子树存**，不存整棵树，每条记录同时留改动前与改动后两份。

| 操作 | 快照对象 |
| --- | --- |
| 内容块增删改移 | 该章节节点 |
| 章节标题、编制说明 | 该章节节点 |
| 复制章节、裁剪章节 | 父节点，因为动的是父节点的子级名单 |

撤销写回 `before`、重做写回 `after`，不需要为每个操作单独实现反向指令。理由很实在：
内容块没有稳定 id，按下标记反向会在插入删除之后错位；子树快照只认节点身份，而节点 id 稳定。

上层的包装是 `ProjectService.withSnapshot(label, scope, coalesceKey, action)`：入口先取
`scope.snapshot()` 作 `before`，跑 action，成功后取一份作 `after` 入栈；action 抛错就原样抛出
且不入栈。界面传进来的每一次编辑都经这里，写回时 `restoreSnapshot()` 用节点 id 找到活着的那个
节点，调 `restoreFrom()` 把子树摊回去；万一那个节点已经不在了，退回根，至少不把这一步丢掉。

一条记录的体积与子树成正比，所以栈的上限有两道，先到先限：

| 上限 | 值 | 超了怎么办 |
| --- | --- | --- |
| 步数 | 100 步（`HISTORY_MAX_STEPS`） | 从最旧的一条开始丢 |
| 累计字节 | 32 MB（`HISTORY_MAX_BYTES`） | 从最旧的一条开始丢，但**至少留一条** |

字节量由 `estimateSnapshotBytes()` 现算：逐节点累加标题、编制说明与各内容块的
`JSON.stringify` 长度，另加每节点 128 字节的固定开销。它量级对就够，不追求精确，中文按字符数
算偏低估。不逐块 stringify 整棵树，是因为那样既慢又会被 `parent` 环挡住。

不采用整树深拷贝：真实工程里一个章节的子树通常只有几 KB，而整棵树会随章节数增长，
100 步下来内存不可控。

## 4 三个入口与历史面板

### 界面拿到的栈状态

`historyState()` 返回一个固定的形状，界面按它驱动按钮与两段列表：`canUndo` 与 `canRedo`
决定按钮是否置灰；`undoLabel` 与 `redoLabel` 是悬停提示里的动作名，栈空为 `null`；`steps`
是已应用的步数；`undoLabels` 是已应用的步骤名，**旧到新**，界面按倒序显示；`redoLabels`
是已撤销的步骤名，**下一个要重做的排在最前**。累计字节数不给界面，它只用于栈自己的上限判定。

### 快捷键

| 键 | 动作 |
| --- | --- |
| `Ctrl+Z` | 撤销 |
| `Ctrl+Shift+Z` | 重做 |
| `Ctrl+Y` | 重做 |
| `Ctrl+S` | 保存 |

撤销与重做的监听挂在 `window` 的**捕获阶段**，按下时先 `preventDefault`，一律走应用级撤销。
这条取舍是明确的：让浏览器自己撤销文本框里的文字，会让界面与内存里的树分叉，分叉之后保存
下去就是脏数据；逐字撤销的损失由 600 毫秒的合并窗口兜住，一次撤销退掉一小段输入而不是整篇。

设置、导出与模板编辑页打开时不动键盘，免得把那些弹层里输入框的撤销也吃掉。

### 按钮

「撤销」「重做」两个按钮与「历史」开关放在视图切换（编辑 / 预览）那一行的左侧。栈空时按钮
置灰，悬停提示写明最近一步的动作名，例如「撤销：删除内容」「重做：修改标题」。

**界面不拿自己缓存的 `canUndo` 当门闸**：撤销与重做一律调主进程，空栈的拒绝在界面吞掉、
不弹提示。缓存的按钮状态可能因为刷新竞态，或外部写入（探针、脚本直接调 IPC）而落后，
落后时按了没反应比多打一次 IPC 更糟。

### 历史面板的读法

面板按 Word 的读法列历史，**列出来的每一条就是一步动作**，点它即退到这一步之前：

| 段 | 顺序 | 点一条的效果 |
| --- | --- | --- |
| 已应用 | 从上到下由近及远 | 把这一步连同它后面的一起退掉，点最旧那条就是回到最初 |
| 已撤销 | 下一个能重做的排最上 | 重做到这一步 |

界面上点某一条传的是 `keep`，含义是「保留多少步已应用的编辑」，`0` 表示回到最初。
主进程收到后先把它夹在 `0` 到总步数之间，再反复撤销或重做：往少了走到 `keep`，往多了补回到
`keep`，**最后一次搬动的子树快照就是结果**，它的节点 id 作为 `focusNodeId` 一并回给界面。
跳转不在栈上再记一步，只移动当前位置。两段列表都空时面板显示「还没有可撤销的编辑」。

历史里**不列「当前状态」**：它不是一个动作，点了等于什么都没发生。

### 撤销之后界面怎么恢复

撤销、重做与跳转返回的载荷与「打开工程」同一形状（`info` 加 `root`），外加 `history` 与
`focusNodeId`，界面**整棵替换**，不另造增量协议。选中项的恢复顺序是：

1. 原来的选中项在新树里还在，保持不动；
2. 不在了就退到这一步动的那个章节（`focusNodeId`）；
3. 再不在就退回根。

撤销与重做不是与增量更新并行的另一条路，它就是「换一棵树」，所以 `AppContext` 用一个
`applyHistoryResult()` 收口，不分散在各组件里。

## 5 挂起编辑与撤销的顺序

内容编辑走 600 毫秒防抖，撤销走应用级快捷键，两条路各走各的。**撤销之前必须先把挂起编辑真的
写完**，否则撤掉的是上一步，而那一次打字随后自己写回来，用户看到的是「按了 Ctrl+Z，字还在」。
围绕这条口径有两处实现细节，都是必需的。

### 一、`flushAll` 要真的等

`AppContext.flushAll()` 取各页注册的 flush 函数，逐个 `await`，再用 `Promise.all` 收口；
注册表与 `registerFlushAll()` 的类型都是 `() => void | Promise<void>`。`runHistory()` 在发起
撤销请求之前调它。

`NodePage.flushPending()` 是 `async` 的：把标题、编制说明与各内容块的写入收集成
`writes` 数组，`await Promise.all(writes)`。调用它的地方本来就有 `await`（加块、删块、移动、
换类型、保存、切节点），此前那些 `await` 等于白等；组件卸载那一处刻意写成
`() => void flushPending()`，要走了不等结果。

### 二、撤销之后界面要按 store 覆盖回来

`NodePage` 与 store 对账那段的跳过条件不能只看 store 侧的签名。用户刚打的字先落在本地
（防抖缓冲里），store 还没动；撤销把 store 退回原名，**签名正好回到上一次对账时的那个值**，
按签名判就会跳过同步，那次打字留在界面上。所以跳过条件是「store 签名没变**且界面那份块序列的
镜像也还跟它一致**」（`blocksRef`）。界面已经分叉就必须按 store 覆盖回来。

对账还有一条并行的目的：保住块的稳定键。块没有 id，键是按块对象配的（`blockKeys`），
结构变更（增删移）由发起方登记，对账时按登记把键跟着搬；只在长度与预期吻合时才采纳，
否则整批换新键。宁可重挂载，也不能张冠李戴——键配错会让正在编辑的光标与滚动位置挂到别的块上。

标题与编制说明也要**回写输入框**：撤销一步标题改动时，树与库已经退回去了，而非受控输入框只在
换章节时重建，不回写就会出现「框里还留着新字」。回写的条件是节点值变了且本地不脏，
正在输入时不打断光标。

## 6 已知边界

- **撤销后选中项不写回 `ui_state`**。`ui_state` 存的只是选中的章节 id，它不参与撤销，
  重启后仍然读上次保存的那个章节；
- **写入失败时界面不回滚本地那份编辑**。失败会弹主进程给的那句原因，数值要等下一次对账才回退。
  失败本身罕见，且要修得把「哪一次写入失败了」一起记下来；
- **重做栈不参与字节上限的淘汰**。`evict()` 只在 `push` 时跑，且只裁撤销栈；大量撤销之后再
  编辑，那些已撤销的记录会随新编辑一起被清掉，不会长期占着内存；
- **界面上的「无法撤销」那句提示**讲的是某次操作的后果本身，与撤销栈无关，栈里那一步照常撤得回来。

明确的非目标：不做跨工程、跨会话的持久化历史，不做逐字符撤销，不做协作或多人合并，
也不把撤销做进 CLI 与导出链路。

| 保存点 | `packages/core/src/tree.ts`：`DocumentNode.snapshot()` 与 `restoreFrom()` |
| 主进程 | `packages/desktop/src/main/services/project-service.ts`：`withSnapshot()`、`undo()`、`redo()`、`jump()`、`historyState()`、`restoreSnapshot()` |

| 渲染层状态 | `state/AppContext.tsx`：`undo`/`redo`/`jumpHistory`/`historyState`/`flushAll`/`applyHistoryResult` |
| 界面 | `components/editor/HistoryControls.tsx` 两个按钮加一张历史面板 |
| 挂起编辑 | `components/editor/NodePage.tsx`：`flushPending`、`blocksRef` 对账、标题与说明回写 |

快照栈是纯函数、无 I/O 的一层，可以脱离 Electron 单测，覆盖合并、封口、上限淘汰、清栈与
重做失效。修改这一块时先改 `history.ts` 的行为，再看主进程与界面的两处消费点是否还成立。

## 8 自检

撤销这个能力有一份界面级自检：`pnpm check:undo`，起真实 Electron 走一遍物理点击，夹具是权限
那份（全开章节第 4 块是自由表）。它验两组，**每组都同时读界面与库**：

1. 表格缩容：改列数后撤销按钮报得出步名、历史面板列得出这一步、点撤销后列数/表头/数据逐值
   回到缩表前、保存落盘也是缩表前的样子；再缩一次并先保存，撤销照样退得回来；
2. 刚打完字就按 `Ctrl+Z`：分三个小 case，打完立刻撤销、打完等 900 毫秒再撤销（对照）、
   打完立刻撤销并等 3 秒看会不会自己回来。

只读界面会被「界面没跟上」骗过去，只读库会漏掉第二种毛病，所以两处都要读。自检脚本在本机
`localscripts/`，不入库，跑法与边界见 [DESIGN-09-质量门禁与发布.md](DESIGN-09-质量门禁与发布.md)。

改到这一块时的惯例：先跑几秒钟的 `pnpm typecheck`，再跑它这一份 `pnpm check:undo`，
界面那几份自检需要先 `pnpm build` 才有产物可点。
