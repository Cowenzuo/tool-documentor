# PLAN-11 模板编辑模式方案

> 现在模板全靠外部产出：在另一个仓库里手写 JSON、手改 DOCX 骨架，程序只负责只读加载。
> 本文分析这套产线的问题，给出在软件内编辑模板的范围、分层与取舍，并列出需要拍板的问题。
> **状态：只出方案，未实施。**

## 1 现状

一套模板由两部分组成，都放在模板仓库（`tool-documentor-template`，与软件仓库分开）：

| 部分 | 文件 | 规模 | 现在怎么产出 |
| --- | --- | --- | --- |
| 结构模板 | `packages/structures/<名>/<名>-structure.json` | 14 到 94 KB | 照《03-新建结构模板指引》手写：节点树、标题级别、节点开关、每个节点的内容块定义与锁档位、以及写给文档作者看的填写说明 |
| 样式模板 | `packages/styles/<名>/<名>-stylemap.json` + `<名>-style/`（解包的 DOCX 骨架） | 映射 1.6 KB，骨架含 styles.xml 与 numbering.xml | 在 Word 里做好版式，解包，再手写 21 个逻辑样式键到 styleId 的映射 |

应用侧的模板能力只有三件：设置里配置模板目录、向导里选模板、`templates:diagnose` 给一份加载报告
（哪些目录加载了几个、哪些条目被跳过、可疑取值在哪）。校验则另有一份实现：模板仓库的
`dev-scripts/check-templates.cjs`，546 行，检查节点开关、锁取值、内容块、样式键是否都能在骨架里
找到、题注节点、编号起始值等。

## 2 痛点

1. **手写大 JSON**：438c-sdd 那种 94 KB 的文件靠文本编辑器维护，缩进、字段顺序、漏写全靠人盯；
2. **校验两套口径**：模板仓库的脚本与产品里的加载器是两份实现，规则早晚分叉；
3. **试错链长**：改完模板必须先回软件里新建工程，才知道结构对不对、锁生效没有、导出什么样；
4. **骨架只能人改**：styles.xml 与 numbering.xml 是 Word 的版式资产，程序目前一点忙帮不上；
5. **说明文字没地方看**：节点上的 `description` 是写给文档作者看的填写指引，现在只以文本形式躺在 JSON 里。

## 3 分层与范围

### 阶段一 模板浏览与结构编辑（核心，先做）

- **入口**：独立的模板编辑模式，与文档编辑器分开，不打开工程、不进撤销栈；
- **左栏**：模板目录与模板列表，结构模板与样式模板分组，标出来源目录与问题数量；
- **中栏**：节点树，复用现有树的视觉语言与交互（增删、上下移、缩进层级）；
- **右栏**：选中节点的表单。节点部分有标题、标题级别、节点类型、`copyable`、`deletable`、
  `allowContentBlocks`、说明文字；内容块部分是可增删的卡片，每张卡片给类型、初始内容与
  `lock` 档位（PLAN-09 的三档）；
- **保存**：写回结构模板 JSON，保留原有缩进与字段顺序；
- **校验**：即时显示问题，有 error 时不许保存；
- **试跑**：一键用当前模板实例化一个临时工程并导出，产物落 `temp/`，可直接 Word 回读。

### 阶段二 样式映射编辑

- 列出骨架 `word/styles.xml` 里真实可用的样式（styleId、名称、段落或字符），把 21 个逻辑键
  做成下拉选择，缺键与指向不存在样式的即时报错；
- 暴露 `captionNumbering`（auto、field、static 与 `chapterStyleNames`），`headingStarts`
  从 `numbering.xml` 读出后只读展示；
- **骨架本身不编辑**：改版式仍在 Word 里做，程序只做映射与校验。

### 阶段三 派生与导入（风险最大，按需）

- 从真实工程反推结构模板：把一棵文档树抽成节点定义，初始内容留空，锁档位留给作者补；
- 导入一份 DOCX 当骨架：检查必需部件，缺的补出，并生成一份未填完的 stylemap 草稿。

## 4 关键取舍

1. **编辑对象只有 JSON，骨架是只读资产**。程序拼装 styles.xml 与 numbering.xml 等于重造 Word 的
   版式系统，风险与收益不成比例；
2. **校验一份实现**。把 `check-templates.cjs` 的规则并进 core，做成
   `validateStructureTemplate` 与 `validateStyleTemplate`，编辑模式、加载报告与模板仓库的脚本
   共用同一份；两处规则不一致时以 core 为准；
3. **写入安全**。原子写（临时文件加改名）、写前备份 `.bak`、写前必须零 error、保留原缩进与字段
   顺序；只写模板目录里的文件，绝不碰 `.dproj`；
4. **模板仓库当普通目录**。它受 git 管理，编辑模式保存后由作者自己提交；界面上要能看出这个目录
   是受版本控制的，别让人以为程序会自动提交；
5. **试跑即验收**。模板对不对，用"新建一个临时工程并导出"来判，比任何静态检查都硬。

## 5 与现有能力的关系

| 现有能力 | 在编辑模式里的角色 |
| --- | --- |
| 结构树的视觉与交互 | 直接复用，属性换成模板字段 |
| 块编辑器的字段表单 | 复用输入控件，去掉"文档内容"的语义 |
| 加载报告 `templates:diagnose` | 作为模板列表上的问题徽标数据源 |
| 预览与导出链路 | 试跑阶段的执行者 |
| 模板目录设置 | 编辑模式的工作根 |
| 锁（PLAN-09） | 编辑模式是锁声明的唯一入口，取代手写 |
| 题注口径（PLAN-07） | 阶段二暴露样式模板里的 `captionNumbering` |

不混的地方：编辑模式不打开工程、不进撤销栈（撤销栈是文档会话级的）、不做模板文件的自动提交。

## 6 验收

- 本机单测：校验规则（把 `check-templates.cjs` 的用例搬过来）、写回后与原文件的差异只含被改字段、
  写失败不留半截文件；
- 本机 E2E：在编辑模式里新建结构模板、加两章、加一个带锁的表格块、保存，再用它新建工程，
  树上出现该结构且锁标记正确，导出成功；
- 真实模板：对模板仓库里 5 个结构模板做一次只读校验，结论必须与 `check-templates.cjs` 一致，
  这是"口径统一"的证据。

## 7 非目标

- 不编辑 DOCX 骨架的样式与编号；
- 不做版式设计器（页边距、字体、缩进的所见即所得面板）；
- 不把模板编辑并入撤销栈，不做模板文件的自动提交；
- 不在本方案里做模板的市场、分发或版本升级。

## 8 待拍板

1. **范围**：先做阶段一（结构模板），还是把阶段二（样式映射）一次做完？
2. **入口形态**：独立窗口，还是设置里的一个页签？
3. **模板清单**：新建或删除模板时由应用维护 `manifest.json`，还是仍然手写？
4. **校验归属**：并进 core 后，模板仓库改为引用它（需要定跨仓库依赖方式），还是先复制一份、
   稳定后再合并？
5. **改名与删除**：要不要做？它要同时动目录名、manifest 与潜在引用，而且要写进另一个仓库。
