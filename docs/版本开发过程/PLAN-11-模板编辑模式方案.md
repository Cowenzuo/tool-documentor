# PLAN-11 模板编辑模式方案

> 现在模板全靠外部产出：在另一个仓库里手写 JSON、手改 DOCX 骨架，程序只负责只读加载。
> 本文分析这套产线的问题，给出在软件内编辑模板的范围、分层与取舍，并列出需要拍板的问题。
> **状态：只出方案，未实施。** 已定口径：结构模板可以直接编辑；样式模板不直接编辑，
> 用户提供现成样式文件，程序只做解包、部件检查与那张对照表的编辑。

## 1 现状

一套模板由两部分组成，都放在模板仓库（`tool-documentor-template`，与软件仓库分开）：

| 部分 | 文件 | 规模 | 现在怎么产出 |
| --- | --- | --- | --- |
| 结构模板 | `packages/structures/<名>/<名>-structure.json` | 14 到 94 KB | 照《03-新建结构模板指引》手写：节点树、标题级别、节点开关、每个节点的内容块定义与锁档位、以及写给文档作者看的填写说明 |
| 样式模板 | `packages/styles/<名>/<名>-stylemap.json` + `<名>-style/`（解包的 DOCX 骨架） | 映射 1.6 KB，骨架含 styles.xml 与 numbering.xml | 在 Word 里做好版式，解包，再手写 21 个逻辑样式键到 styleId 的映射 |

应用侧的模板能力只有三件：设置里配置模板目录、向导里选模板、`templates:diagnose` 给一份加载报告
（哪些目录加载了几个、哪些条目被跳过、可疑取值在哪）。校验则另有一份实现：模板仓库的
`dev-scripts/check-templates.cjs`，546 行，检查节点开关、锁取值、内容块、样式键是否都能在骨架里
找到、题注节点、编号起始值等。

## 2 痛点

1. **手写大 JSON**：438c-sdd 那种 94 KB 的文件靠文本编辑器维护，缩进、字段顺序、漏写全靠人盯；
2. **校验两套口径**：模板仓库的脚本与产品里的加载器是两份实现，规则早晚分叉；
3. **试错链长**：改完模板必须先回软件里新建工程，才知道结构对不对、锁生效没有、导出什么样；
4. **骨架只能人改**：styles.xml 与 numbering.xml 是 Word 的版式资产，程序目前一点忙帮不上；
5. **说明文字没地方看**：节点上的 `description` 是写给文档作者看的填写指引，现在只以文本形式躺在 JSON 里。

## 3 分层与范围

### 阶段一 模板浏览与结构编辑（核心，先做）

- **入口**：独立的模板编辑模式，与文档编辑器分开，不打开工程、不进撤销栈；
- **左栏**：模板目录与模板列表，结构模板与样式模板分组，标出来源目录与问题数量；
- **中栏**：节点树，复用现有树的视觉语言与交互（增删、上下移、缩进层级）；
- **右栏**：选中节点的表单。节点部分有标题、标题级别、节点类型、`copyable`、`deletable`、
  `allowContentBlocks`、说明文字；内容块部分是可增删的卡片，每张卡片给类型、初始内容与
  `lock` 档位（PLAN-09 的三档）；
- **保存**：写回结构模板 JSON，保留原有缩进与字段顺序；
- **校验**：即时显示问题，有 error 时不许保存；
- **试跑**：一键用当前模板实例化一个临时工程并导出，产物落 `temp/`，可直接 Word 回读。

### 阶段二 样式对照表编辑（不改骨架）

已定口径：**样式模板不直接编辑**，用户仍然提供一份现成的样式文件（DOCX 或已解包的骨架目录），
程序只做解包与必需部件检查，一个字节的 XML 都不改；可编辑的是结构模板与样式之间的那张
**对照表**，也就是 stylemap 里的 `styleMap` 与 `captionNumbering`。这样缺映射时能当场补上，
而不是回头去手改 JSON。

- **导入样式文件**：选一个 `.docx` 或已解包的骨架目录。是 `.docx` 就解包进模板目录，随后检查
  必需部件（`styles.xml`、`numbering.xml`、`document.xml` 与关系表）是否齐全，缺了就报错；
- **列出可用样式**：从 `styles.xml` 读出 styleId、样式名、段落或字符类型、字号这类可读属性，
  作为对照表下拉的选项；
- **对照表视图**：每行是一个逻辑键，列出用途说明、当前指向的样式（下拉）、是否必需、以及状态；
  指向不存在的样式、必需键缺失都当场标红；
- **必需键按实际用法算**：不是把 21 个键一刀切，而是按这份结构模板里真正用到的块推导
  （有表格才要 `table.caption` 与 `table.header`，有图才要 `figure.caption`，有序列表用到第几层
  才要 `list.ordered.N`），这套推导模板仓库的校验脚本里已经有；
- **缺映射时先给草稿**：导入样式文件后按样式名做一次模糊匹配，把能认出来的键先填上
  （`标题 1`、`heading1`、`正文`、`body` 这类），剩下的留空待填，避免从零开始；
- **引用关系也在这一步设**：结构模板的 `styleTemplate` 与 `styleTemplates` 从可用样式模板里选，
  免得映射改好了、引用没对上；
- **共用要提示**：同一份映射可能被多个结构模板共用，编辑器要显示"这份对照表还被谁用"，
  并给一个"另存为本结构模板专用"的动作，避免改一处影响别人。

### 阶段三 派生（风险最大，按需）

- 从真实工程反推结构模板：把一棵文档树抽成节点定义，初始内容留空，锁档位留给作者补。

## 4 关键取舍

1. **编辑对象只有 JSON，骨架是只读资产**。程序拼装 styles.xml 与 numbering.xml 等于重造 Word 的
   版式系统，风险与收益不成比例；用户提供样式文件，程序只解包、只校验部件齐全；
2. **映射留在样式侧，不搬进结构模板**。对照表的物理落点仍是 stylemap 文件，与现在的加载口径
   一致，不引入第二处来源；代价是同一份映射可能被多个结构模板共用，所以要显示影响面并支持
   "另存为专用"；
3. **完整性按实际用法判定**。缺映射的标准是"这份结构模板用到的键里有没有缺、指向的 styleId
   在骨架里在不在"，不是把全部逻辑键一刀切；
4. **校验一份实现**。把 `check-templates.cjs` 的规则并进 core，做成
   `validateStructureTemplate` 与 `validateStyleTemplate`，编辑模式、加载报告与模板仓库的脚本
   共用同一份；两处规则不一致时以 core 为准；
5. **写入安全**。原子写（临时文件加改名）、写前备份 `.bak`、写前必须零 error、保留原缩进与字段
   顺序；只写模板目录里的文件，绝不碰 `.dproj`；
6. **模板仓库当普通目录**。它受 git 管理，编辑模式保存后由作者自己提交；界面上要能看出这个目录
   是受版本控制的，别让人以为程序会自动提交；
7. **试跑即验收**。模板对不对，用"新建一个临时工程并导出"来判，比任何静态检查都硬。

## 5 与现有能力的关系

| 现有能力 | 在编辑模式里的角色 |
| --- | --- |
| 结构树的视觉与交互 | 直接复用，属性换成模板字段 |
| 块编辑器的字段表单 | 复用输入控件，去掉"文档内容"的语义 |
| 加载报告 `templates:diagnose` | 作为模板列表上的问题徽标数据源 |
| 预览与导出链路 | 试跑阶段的执行者 |
| 模板目录设置 | 编辑模式的工作根 |
| 锁（PLAN-09） | 编辑模式是锁声明的唯一入口，取代手写 |
| 题注口径（PLAN-07） | 阶段二暴露样式模板里的 `captionNumbering` |

不混的地方：编辑模式不打开工程、不进撤销栈（撤销栈是文档会话级的）、不做模板文件的自动提交。

## 6 验收

- 本机单测：校验规则（把 `check-templates.cjs` 的用例搬过来）、必需键推导（按块用法推导出的键集
  与脚本一致）、写回后与原文件的差异只含被改字段、写失败不留半截文件；
- 本机 E2E：在编辑模式里新建结构模板、加两章、加一个带锁的表格块、保存，再用它新建工程，
  树上出现该结构且锁标记正确，导出成功；
- 对照表：导入一份样式文件后自动草稿能填上大部分键；故意删掉一个必需映射时编辑器报红并拒绝保存；
  指向骨架里不存在的 styleId 时报红；
- 真实模板：对模板仓库里 5 个结构模板做一次只读校验，结论必须与 `check-templates.cjs` 一致，
  这是"口径统一"的证据。

## 7 非目标

- 不编辑 DOCX 骨架的样式与编号，不做版式设计器（页边距、字体、缩进的所见即所得面板）；
- 不把模板编辑并入撤销栈，不做模板文件的自动提交；
- 不在本方案里做模板的市场、分发或版本升级。

## 8 待拍板

已定下的两条：结构模板可以直接编辑；样式模板不直接编辑，用户提供样式文件，程序只做解包、
部件检查与对照表编辑。

还需拍板：

1. **入口形态**：独立窗口，还是设置里的一个页签？
2. **清单维护**：新建或删除模板时由应用维护 `manifest.json`，还是仍然手写？
3. **校验归属**：并进 core 后，模板仓库改为引用它（需要定跨仓库依赖方式），还是先复制一份、
   稳定后再合并？
4. **改名与删除**：要不要做？它要同时动目录名、manifest 与潜在引用，而且要写进另一个仓库。
5. **样式文件的常态**：作者平时交的是 `.docx` 原文件，还是已经解包的骨架目录？这决定导入那一步
   是"每次都解包"还是"目录已就位只做校验"。
