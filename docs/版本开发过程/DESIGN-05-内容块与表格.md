# 内容块与表格

> 本页回答"内容块有哪几种、属性怎么落库、表格的形状与内容怎么分、纵向合并按什么判定"。
> 判定口径的唯一事实源是 [表格与合并.md](../WORD解压结构研究/表格与合并.md)，本页与它冲突时以它为准；
> 代码侧的事实源是 `packages/core/src/blocks.ts`、`table-limits.ts`、`table-merge.ts`。

## 1 八种内容块与各自的属性

类型是一个固定的枚举，顺序与老版数据保持一致（`BLOCK_TYPE_NAMES`，下标 0..7）：

| 下标 | 类型名 | 界面名 | 属性字段 |
| --- | --- | --- | --- |
| 0 | `text` | 文本 | `content`（多行字符串） |
| 1 | `image` | 图片 | `imagePath`（相对工程目录的路径）、`caption`（图名／题注） |
| 2 | `table` | 表格 | `caption`、`rows`、`cols`、`headers`、`data`、`rowSpans?`、`mergeVertical?` |
| 3 | `formula` | 公式 | `latexCode`（LaTeX 源码） |
| 4 | `code` | 代码 | `language`、`code` |
| 5 | `mermaid` | 流程图 | `caption`、`code`（Mermaid 源码） |
| 6 | `orderedList` | 有序列表 | `items`（字符串数组，一项一行） |
| 7 | `unorderedList` | 无序列表 | `items`（同上） |

三种"装内容的地方"值得单独记住，换类型的搬运规则就建在这上面（见
[DESIGN-06-权限与锁.md](DESIGN-06-权限与锁.md) 第 9 节）：

- **主文本**：`content` / `items` / `code` / `latexCode` 各一处，按行读出、按行写回；
  表格是二维的，一行一格、格间用制表符；**图片没有主文本**；
- **题注位**：只有表格（`caption` 是表名）、图片（图名）、流程图（图名）三处；
- **形状类字段**：表格的 `cols` / `headers` / `rowSpans` / `mergeVertical`，图片的 `imagePath`。
  换类型时它们不跟过去 —— 那是"换类型"三个字的定义。

每条块还可以带一个可选的模板锁 `lock`（`keep` / `readonly`，以及作废的旧档位 `type`）。
它不是某一类块的属性，而是八种块共有的可选字段（`BlockLockProps`），语义见
[DESIGN-06-权限与锁.md](DESIGN-06-权限与锁.md)。

### 1.1 新旧属性名的对应：模板 JSON / 实例 JSON 里的 `content`

工程库与文档树里的属性名是上表那一套；模板 JSON 与实例 JSON 走的是另一套写法，
两者在载入时被翻译一次，主文本统一叫 `content`：

| 块类型 | 模板／实例 JSON | 块对象 |
| --- | --- | --- |
| `text` | `content` | `content` |
| `mermaid` | `content` | **`code`** |
| `code` | `content` + `language` | `code` + `language` |
| `formula` | `content` | `latexCode` |
| `image` | `content`（路径）+ `caption` | `imagePath` + `caption` |
| `orderedList` / `unorderedList` | `items` | `items` |
| `table` | `caption` / `rows` / `cols` / `headers` / `data` / `mergeVertical` | 同名 |

所以"模板里写着 `content`"与"块上是 `code`"不是笔误。模板里的 `type` 写错或写了程序不认识的
取值时，那个块会在实例化时被跳过（`manager.ts` 只挑认识的类型），实例 JSON 同理
（`instance.ts` 只认 text/heading、有序与无序列表、表格、mermaid 五种，其它返回 `null`）。

## 2 块怎么落库：数字类型 + `props_json`

`content_block` 表只有两个字段装块的数据（其余列见
[DESIGN-04-工程数据与存储.md](DESIGN-04-工程数据与存储.md) 第 3.3 节）：

| 列 | 写什么 | 读什么 |
| --- | --- | --- |
| `block_type` | 类型下标转成字符串：`String(blockTypeIndex(type))` → `'0'`..`'7'` | `parseBlockType` 宽松解析 |
| `props_json` | `JSON.stringify(propsOf(block))`，**不含 `type`** | `JSON.parse` 后交给 `blockFromDb` |

- **`lock` 跟着 `props_json` 走**：它和 `content`、`data` 一样是块数据的一部分，不是另外一张表
  的列。这样"锁跟着块走"是天然的 —— 插入、删除、换位都不会让锁跑到别的块上；
- **写库前会拦住未知类型**：`blockTypeIndex` 对枚举外的类型直接抛错，
  `createBlock` 对枚举外的类型也抛错。写进去一个 `-1` 之类的值会让整个工程再也打不开
  （载入时认不出类型就是硬失败），所以宁可在写入那一刻就炸，不留到读的时候；
- **表里的 `id` 与块的身份无关**：块的身份是"某节点下的第几块"，见 DESIGN-04 第 3.5 节。

## 3 表格：形状与内容之分

表格是唯一一类"改一处字段就可能改变表本身"的块，所以它的字段被分成两组：

| 组 | 字段 | 改它算 |
| --- | --- | --- |
| **形状** | `cols`、`headers`、`rowSpans`、`mergeVertical` | 改形状：要"排版开着且块上没有锁" |
| **内容** | `data`（每个单元格的值）、`caption` | 改内容：只要"编辑开着且不是只读" |
| **提示性元数据** | `rows` | 都不算：对渲染与导出没有影响 |

- **写入侧的判定**是 `tableShapeChanged`：`cols`、`headers`、`rowSpans`、`mergeVertical`
  四项任一变化就按"换形状"处理，与"换类型"走同一条拒绝路径。`caption` 与 `data`
  不在这四项里 —— 表名与单元格是内容；
- **界面上的对应**：表头输入框与行列数输入框、合并勾选框一起按 `shapeLocked` 置灰，
  单元格输入框只受"只读"档限制。所以"类型限制编辑"档的表，用户能填数据、填不了表头；
- **`rows` 只是提示**：正文行数以 `data.length` 为准，`bodyRowCount()` 直接忽略传入的 `rows`。
  历史口径曾把表头算进 `rows`，渲染或导出若拿它当上界，`rows < data.length` 时会静默丢掉行尾数据。
  因此渲染、预览、导出**都逐行走 `data`，一行不多一行不少**；
- **`rowSpans` 的坐标系**：`{ 列号: [[起始行, 跨几行], ...] }`，行号按 `data` 下标、**不含表头**。
  它显式表示跨行，不看内容，因此值可以照常保留 —— 取消合并就能恢复原状。

## 4 纵向合并：显式跨度与兼容判定取并集

同一条判定被三处消费：编辑区的提示、预览的跨行、导出的合并。实现只有一份：
`resolveTableMerges`（`core/table-merge.ts`），返回与 `data` 同形状的矩阵 ——
起点格给出 `rowSpan`，被覆盖格标记 `covered`。渲染进程从子路径
`@documentor/core/table-merge` 导入，不从包根导入（包根挂着 SQLite 存储）。

两种来源**各管一段，取并集**，不是二选一：

1. **显式跨度 `rowSpans` 逐格优先**。它认领过的格子随即被标记，第 2 条不再碰它；
2. **兼容判定**在 `mergeVertical: true` 时补上没被认领的部分，两种形态：
   - **连续相同**：连续若干行 trim 后非空且完全相同 → 合成一格；
   - **空串向上合并**：非空值后面跟的**连续空串**并入上面那一格（"留空 = 续格"的写法），
     组延续到下一个非空值为止。列首的空串没有可并入的对象，跳过。

旧口径是"有 `rowSpans` 就整体接管"，一张表只要带了不完整的跨度，别处该合的地方就静默不合。
现在加跨度只会增加合并，不会让别处的合并消失 —— 这也是兼容判定能安全留在产品里的原因：
它靠内容推断，只认得上面两种形态；想把跨行与内容彻底解耦，用 `rowSpans`。

**列数口径四处必须一致**（判定、编辑区、预览、导出）：取表头长度、提示性 `cols`、
各数据行长度的**最大值**，至少 1 列；**没有数据行时按 0 行返回空网格**，不凭空造出合并。
只按数据行宽度算会漏掉两类列（表头比数据行宽的、`cols` 声明的），定义在这些列上的显式跨度
会被当成越界丢掉。

越界与重叠怎么处理：

- 跨度超出行数时截到表尾，起点在表外、或截短后不足 2 行的丢弃（单行没有可合并的对象）；
- 列号非法（非整数、负数、`>=` 列数）的整列丢弃；
- 同一格被两个跨度重复认领时**只认先到的那个**，不产出非法的重叠合并；
- 读库时 `parseRowSpans` 先规整一遍：非数组、元素不是 `[起始行, 跨几行]`、跨度 `< 2` 的一律丢弃，
  一个跨度都不剩时这个字段就不写出来（不留空对象）。

**表头行不参与合并**（判定与导出两侧同一条），合并只改显示与导出，**不改 `data` 里的值**。

同一个判定在三处消费，读法各不相同：

| 消费方 | 取矩阵里的什么 |
| --- | --- |
| 编辑区 | 被覆盖的格子加弱化样式（内容照常可编辑），勾选时统计"已合并 N 处" |
| 预览 | 起点格渲染跨行，被覆盖格不渲染 |
| 导出 | 起点格写 `<w:vMerge w:val="restart"/>` 加居中，续格写空的 `<w:vMerge/>` 与空段 |

导出那一侧的 XML 顺序与空段要求见 [表格与合并.md](../WORD解压结构研究/表格与合并.md)：
`w:tcPr` 的子元素顺序是强制的（`w:tcW` → `w:vMerge` → `w:vAlign`），续格必须是空段，
内容只在起点格出现一次；列数不齐的行会按列数补空格子，缺格会让 Word 自己补列、边框与合并错位。

## 5 块的写入路径

块的每一次改动都走同一批主进程接口，**校验先做、改动后做**，被拒绝的写入不入库也不入撤销栈：

| 接口 | 先过哪一关 | 落库形态 |
| --- | --- | --- |
| 加块（可带插入位置） | `perms.add`（编辑 × 排版） | 追加或插到指定下标之前 |
| 删块 | `perms.remove`（编辑 × 排版）＋ 块档位不是 `keep` / `readonly` | 从数组里摘掉 |
| 移块（与相邻块换位） | `perms.move`（编辑 × 排版） | 交换两个下标 |
| 改块 | `perms.editContent`（编辑）＋ 只读档另拦内容；换类型／换形状再过排版与块档位 | **整块替换**，但 `lock` 强制取原块的值 |

四条与数据形态有关的事实：

- **改块是整块替换**，不是逐字段合并：调用方给的是"改完之后这一块长什么样"，
  落库时把 `lock` 换成原块的那一份。所以界面上少给一个字段就等于把它清空 ——
  编辑器的做法是 `{ ...block, 改哪个字段就覆盖哪个 }`；
- **加块只给类型**：新块是 `createBlock(type)` 的空块，表格拿到的是 `rows: 0` / `cols: 0` /
  空表头空数据。空表的形状不完整，但加块这条路不跑形状校验 —— "先把空表加进来、再由用户定形状"
  是既有状态，形状是在随后那次改块里定的；反过来说，**外部通道加一张表就必须自带合法形状**
  （`cols >= 1` 且各行补齐到同一列数），否则那一次改块会被写入侧拒绝；
- **写入侧才是最后一道**：界面按同一份判定置灰只是提示，绕过界面（外部工具、写入命令）也得过
  这些判定，判定与拒绝语都取自 `shared/permissionTerms`，见
  [DESIGN-06-权限与锁.md](DESIGN-06-权限与锁.md)；
- **图片是两件事**：换图先由主进程把文件复制进工程 `images/`，再走一次改块把路径写进块。
  如果随后的改块被拒（只读档），文件已经落地但没有任何块引用它 —— 这类孤儿文件当前不做清理。

## 6 界面上限与写入校验

上限定义在 `core/table-limits.ts`，界面与写入侧引用同一组数字：

| 常量 | 值 | 意思 |
| --- | --- | --- |
| `TABLE_MAX_ROWS` | 500 | 界面愿意一次让你编辑的行数 |
| `TABLE_MAX_COLS` | 30 | 同上，列数 |

**这是可用性边界，不是数据合法性上限**：界面每格一个输入框，行 × 列就是 DOM 节点数，
5 000 个输入框已接近卡顿边缘。超出上限的表照常保存、照常导出，界面只提示"建议分批编辑或拆表"；
交付前检查（precheck）会把它数出来报一次。

`checkTableShape` 是唯一一份完整性校验（core 定义，界面、写入命令、导出共用）：

| 检查项 | 结论 | 说明 |
| --- | --- | --- |
| `cols` 不是正整数 | **拒绝写入** | 列数是表的基本形状，0 列的表没有意义 |
| `headers` 非空且长度 ≠ `cols` | **拒绝写入** | 表头要么留空（无表头），要么写满 `cols` 列 |
| 某个 `data` 行的长度 ≠ `cols` | **拒绝写入** | 逐行报出位置；只报前 5 条，避免刷屏 |
| `rows` 给出且 `< data.length` | 只提示 | 历史口径（把表头算进 `rows`），且渲染只认 `data` |

`rows` 这一类只在"声明**少于**实际"（`rows > 0 && rows < data.length`）时说话；
`rows` 为 0 或声明**多于**实际都不提示 —— 措辞与实现一致，都是"明显小于"才算口径错。
要不要把"声明多于实际"也提醒一句，记在 [待办与优先级.md](待办与优先级.md) 里。

写入侧的拦法是"`where !== 'rows'` 的问题一律抛错"，`rows` 那一条只打一条 `console.warn`。
导出侧对同一份判定降级为**警告**：模板、实例 JSON 与老工程带进来的参差表会一路走到导出，
那里不能拦，只把问题说清楚透出来。界面上的对应做法：

- 行列数输入框的最小值直接卡住：行数 `>= 0`、列数 `>= 1`（`applySize` 里 `Math.max(1, cols)`），
  所以界面上造不出 `cols = 0`。**这层守卫只在工程侧的表格编辑器里**：模板编辑器的表格网格
  （`TableGrid.tsx`）与实例 JSON 通道没有它，靠保存时的 `checkTableShape` 与模板校验兜住 ——
  边界上两处宽严不同，是否要对齐记在 [待办与优先级.md](待办与优先级.md) 里；
- 缩容时裁掉的行列**直接落库、不再弹确认**，这一步在撤销栈里（`updateBlock` 存整块快照），
  裁错了撤销一次就回来；
- 每次改尺寸都按新尺寸重算 `rowSpans`（`clampRowSpans`）：列被删掉的整列丢弃、起点在表外的丢弃、
  尾部超出的截短、不足 2 行的丢弃 —— 越界的跨度落到表外会让导出与预览错位。结果与输入没差别
  就不写回；跨度全没了就把 `rowSpans` 字段清掉（与读库侧的"不留空对象"同口径）。

## 7 界面上的合并开关与提示

- 勾选框就是 `mergeVertical`：勾上按第 4 节的规则合并，取消就散开，**单元格内容始终留在原处**，
  所以这一步可逆，撤销即可退回；
- `rowSpans` **只由接手外部数据时带上，程序不主动写它**：界面上没有"把判定结果写成显式跨度"
  的第二次操作，缩表时才按新尺寸裁剪既有跨度；
- 勾选状态下给出"已合并 N 处"（`countVerticalMerges` 数的是 `rowSpan > 1` 的起点格数）；
- 被覆盖的单元格加弱化样式并给一句悬停提示，**仍然可编辑** —— 合并只是显示与导出的行为。

## 8 读写的宽松口径

读库一侧的原则是"值不好看就补默认值，结构坏掉才拒绝载入"（结构坏掉那条见
[DESIGN-04-工程数据与存储.md](DESIGN-04-工程数据与存储.md) 第 8 节）。逐字段的口径：

| 字段 | 读不到／类型不对时 |
| --- | --- |
| `content` / `caption` / `code` / `latexCode` / `language` / `imagePath` | 按字符串读：不是字符串就 `String(v)`，`null` / 缺省为空串 |
| `items` / `headers` | 不是数组就是 `[]`；元素逐个转字符串 |
| `data` | 不是数组就是 `[]`；元素不是数组的那一行按空行看；格值转字符串 |
| `rows` / `cols` | 不是数字就按十进制解析，解不出来是 `0` |
| `mergeVertical` | **只有 `=== true` 才算开**（缺键、`1`、`"true"` 都当关） |
| `rowSpans` | 逐条过滤，坏的一条丢掉；一条不剩就不写这个字段 |
| `lock` | 只认 `type` / `keep` / `readonly` 三个字符串，其它一律丢弃（按不锁处理）并记一条载入警告 |

读写两侧还有两处要一起记住：

- **写入侧不采信调用方给的 `lock`**：`updateBlock` 落库时把档位换回原块的
  `lock: existing.lock`（`...structuredClone(input.block), lock: existing.lock`）—— 否则界面
  一次内容编辑就能把模板的锁悄悄改掉；
- **未识别的属性键在保存时不会留着**：`propsOf` 只输出该类型已知的字段，
  所以"库里多出来一个程序不认识的键"会在下一次保存时消失。模板那边是"未知键原样写回"，
  工程侧相反 —— 差别在于模板 JSON 是作者手写的源文件，工程库是程序自己的产物。

## 9 块的身份与界面稳定键

块在数据里没有稳定 id（身份 = 下标），这件事必须由界面自己补一层：

- 每个下标配一把前端键（`crypto.randomUUID()`），React 用它做 `key`。直接用下标当 key 的话，
  一次"上移"会把两张卡片整体重挂载，正在编辑的光标、滚动位置、图片上传的忙碌态全丢；
- 增删移之后键要跟着搬：发起方在动手前登记这次结构变更（加了／插到哪／删了哪／从哪移到哪），
  对账时按登记加工键。长度与预期不吻合就整批换新键 —— 宁可重挂载，也不能把键张冠李戴；
- 折叠状态是纯界面状态，按节点存在内存里（切走再回来还认得），不落库、不进 `ui_state`；
- 界面缓存的块序列要跟主进程"对账"：主进程的块序列一变就整表覆盖回本地，
  只保留尚未提交的编辑缓冲。撤销之后界面必须能被 store 覆盖回去，否则会出现"树已经退回去了、
  卡片上还留着新内容"。

## 10 编辑界面的落点

- 八种块的编辑器都在 `BlockEditors.tsx`，受控组件：值由 `NodePage` 给，改动即时回传；
- 卡片上下一层的呈现（类型徽标、行内摘要、档位标记、折叠）在 `BlockCard.tsx` 与
  `blockTypes.ts`（标签、徽标、代码语言、空块说明）；
- 界面上的类型菜单与"添加内容"菜单共用同一批标签与说明；
- 表格的编辑单元格、表头、行列数、合并开关的置灰规则见第 3 节，权限本身见
  [DESIGN-06-权限与锁.md](DESIGN-06-权限与锁.md)。

两处容易踩的界面坑，与数据无关但会影响"看到的和库里的是不是一回事"：

- **块的编辑是防抖提交的**（每个下标一个 600ms 定时器）。加块、删块、移动、换类型之前都必须先
  把挂起的编辑写完，否则定时器到点会把旧类型／旧内容的那一份块写回去，用户看到的是"我的操作
  被静默改回来了"；
- **卡片头上的摘要对表格只认 `data` 与列数**，不认 `rows`；折叠后的摘要、徽标与档位标记都按
  当前类型重画，所以换类型之后卡片头会立刻换一身说法。
