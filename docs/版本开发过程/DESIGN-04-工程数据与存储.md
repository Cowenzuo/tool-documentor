# 工程数据与存储

> 本页回答"一个工程在磁盘上由哪些东西组成、数据怎么落进 SQLite、认不出来的数据怎么办"。
> 结论以 `packages/core/src/store.ts`、`anchor.ts`、`tree.ts` 为准；模板引用的唯一权威是
> 模板 uuid，模板名只是给老工程一次认回 uuid 的线索。

## 1 一个工程目录里有什么

工程目录就是锚点文件所在的那个目录，其余一切都相对它定位。

| 件 | 名字 | 谁写 | 说明 |
| --- | --- | --- | --- |
| 锚点 | `documentor.dproj` | 主进程 `writeAnchor` | JSON，工程的身份卡：名字、模板引用、库文件名、时间戳 |
| 工程库 | `documentor.db` | `ProjectStore`（`node:sqlite`） | SQLite，节点树、内容块、界面状态都在这里 |
| 图片 | `images/<uuid>.<ext>` | `importImage` 或渲染层写文件 | 图片一律复制进工程目录，库里只记相对路径 |
| 流程图缓存 | `mermaid/<sha256>.png` | 渲染层按源码哈希写 | 只是缓存，删掉不影响数据，下次渲染会重建 |
| 导出产物 | 用户选定的路径 | 导出链路 | 默认建议 `<工程目录>/<工程名>.docx`，但用户改到别处也照办 |

- **库里记的是相对路径**（`images/xxx.png`），所有读图的地方都按工程目录解析：缩略图、预览、导出
  用的是同一条规则；`writeProjectFile` 还会拒绝越出工程目录的相对路径；
- 老数据里只记了裸文件名（历史脏数据）：读图时先按工程目录找，找不到再回落到 `images/`；
- **锚点不存在就是无效工程**：`openProject` 直接拒绝，不去猜库在哪；
- 锚点里的 `db_file` 决定库文件名，缺省是 `documentor.db`；读锚点时该键缺失即按缺省处理，
  所以手工改过锚点的工程仍能打开。
- **没有伴生的 `-wal` / `-shm` 文件**：打开库时只设了 `PRAGMA foreign_keys = ON`，没有开 WAL，
  所以走的是 SQLite 默认的回滚日志；写入期间目录里可能出现一个临时的 `documentor.db-journal`，
  正常关闭后自行消失，不是工程数据的一部分。

## 2 锚点文件：字段与写回时机

`ProjectAnchor`（`packages/core/src/anchor.ts`）的字段与落盘形态：

| 字段 | 盘上的键 | 缺省 | 说明 |
| --- | --- | --- | --- |
| `version` | `version` | 1 | 锚点格式版本，目前只有 1 |
| `name` | `name` | `''` | 工程名，与库里 `project.name` 同一个值 |
| `template_uuid` | `template_uuid` | `''` | **模板引用的权威** |
| `legacyTemplateName` | `template` | 不写 | 老工程写的模板名；只在没有 uuid 时有意义 |
| `db_file` | `db_file` | `documentor.db` | 库文件名 |
| `created_at` / `updated_at` | 同名 | `''` | 本地 ISO 时间（`yyyy-MM-ddTHH:mm:ss`，无时区） |

写回时机只有两处，都是"保存这件事的一部分"：

1. **新建工程**：`createProject` 建库落盘后立刻写一份锚点，`template_uuid` 就是选的那份模板；
2. **保存**：`saveProject` 先把树整份写进库，再更新锚点的 `updated_at` 并写盘。

锚点的引用字段怎么写，取决于这次会话有没有认到 uuid：

- 认到了（`template_uuid !== ''`）：只写 `template_uuid`，**不再写 `template`**；
- 没认到但手里有老名字：把名字写回 `template`，免得一次保存就把这条线索抹掉；
- 两样都没有：写 `template_uuid: ''`。

落盘顺序是"先库后锚点"，两者是两次独立的写：库写失败会抛错、锚点不动；库写成功而锚点写失败，
这一次保存以异常收场，库已经是新的、锚点还是旧的 `updated_at` —— 工程照常打得开，
时间戳不对不影响读取。

## 3 库表结构：四张表各管什么

建表语句在 `ProjectStore.createSchema()`，与老版工程库的形态对齐，另外加过两列（见第 5 节）。

### 3.1 `project`：一行，工程的身份

| 列 | 职责 |
| --- | --- |
| `id` | 自增主键，程序不读；工程工作区的三个工具脚本也不读（`apply-project` / `view-project` / `verify-project` 都按路径找工程，不认这个号） |
| `name` | 工程名。新建时写入，之后保存**不更新**（改名是另一件事） |
| `template_uuid` | 模板引用的权威列。老库没有这一列，保存时补（第 5 节） |
| `created_at` / `updated_at` | 本地 ISO；`updated_at` 每次保存刷新 |

一行都没有的库（表在、行不在）在打开时报"工程数据异常：project 表读不到"；`name` 只在新建时写，
保存不刷新它 —— 工程改名是另一件事，改的是锚点与库里的同一处口径，不属于保存流程。

老库还有一列 `template_name`（旧版本按名字记引用用的）。现在的读写口径是：

- **读**：按实际存在的列问一遍，有就读出来（`legacyTemplateName()`），没有读成空串；
- **写**：保存只写 `updated_at` 与 `template_uuid`，**不碰 `template_name`**；
- 补 `template_uuid` 列时也不动它 —— 名字是留给"这次还没认出来"的工程下次再认一次的，
  现在删掉就等于把线索丢了。

### 3.2 `node`：文档树

| 列 | 职责 |
| --- | --- |
| `id` | 节点 id，字符串主键；由 `nextNodeId()` 发号 |
| `parent_id` | 父节点 id，根节点为 NULL，外键 `ON DELETE CASCADE` |
| `sort_order` | 同级次序，读的时候 `ORDER BY sort_order` |
| `heading_level` | 0 = 根节点，1..N = 标题级别 |
| `title` / `description` | 章节标题与编制说明 |
| `node_type` | **普通节点一律写空串**（模板定义的 `nodeType` 编辑时不变，不落库）；只有根节点写 `'root'` |
| `is_sub_title` | 是否列表子标题（编号层级里的一档） |
| `sub_title_style` | 子标题编号风格：`numeric` / `alpha` / `alphabetic` |
| `sub_title_auto_number` | 子标题是否自动编号 |
| `copyable` | 权限：复制，缺省 0 |
| `deletable` | 权限：裁剪，缺省 0 |
| `allow_content_blocks` | 权限：编辑（内容块总闸），缺省 1 |
| `allow_layout_edit` | 权限：排版，缺省 1；老库没有这一列 |
| `allowed_child_levels` | 允许的子节点级别，逗号分隔；空 = 不限制 |

- **权限四列是数据，不是缓存**：打开工程时按列读回节点，四个开关跟着节点走，见
  [DESIGN-06-权限与锁.md](DESIGN-06-权限与锁.md)；
- **根节点的行也要写全**：根行只有 `heading_level = 0` / `parent_id = NULL` / `node_type = 'root'`
  三处特殊，标题、编制说明、内容块与四个开关都是真数据，保存时必须一起落库；
- 读树从 `parent_id IS NULL` 的那一行起步，一行都找不到就是"工程数据异常：缺少根节点"。

### 3.3 `content_block`：内容块

| 列 | 职责 |
| --- | --- |
| `id` | 自增主键，**程序不用它**：块的身份就是"某节点下的第几块" |
| `node_id` | 所属节点，外键 `ON DELETE CASCADE` |
| `sort_order` | 节点内的次序，读的时候 `ORDER BY sort_order` |
| `block_type` | 八种类型的数字字符串 `'0'`..`'7'` |
| `props_json` | 该类型的属性对象，**不含 `type`**；模板锁 `lock` 也在这里面 |

块没有稳定 id，这件事有两个直接后果：锁定信息不能按下标另外存一张表（插删之后会错位，
所以 `lock` 写进块数据本身），前端只能用防抖队列的浮动键来避免重挂载。类型与属性的细节见
[DESIGN-05-内容块与表格.md](DESIGN-05-内容块与表格.md)。

### 3.4 `ui_state`：界面状态

`key` / `value` 两列的键值表，只存"下次打开想恢复的界面状态"，不属于文档内容：

| 键 | 存什么 |
| --- | --- |
| `selected_node` | 上次选中的章节 id |
| `editor_view` | 内容视图还是预览视图 |
| `tree_expanded` | 结构栏展开的节点 id 数组（JSON） |

这些值坏掉不影响工程：读不出来就按缺省走。它们**不进撤销栈**，也不随保存时机特殊处理。

### 3.5 id 与次序怎么发

- 节点 id 由 `nextNodeId()` 发号，载入时按库里现存的最大数字 id 播种，避免新节点与旧 id 撞号；
- 内容块没有 id 可用：`content_block.id` 是自增主键，程序既不读也不写它。块的序号完全由
  `sort_order` 决定，而且**每次整份重写都会重新编号**；
- 次序的唯一来源是数组下标：`sort_order` 与内存里的 `contentBlocks[]`、`children[]` 一一对应。
  任何"按 id 找块"的写法都是错的，写入接口收的也是下标（`index` / `from` / `to`）。

## 4 模板引用：uuid 是权威，名字只是线索

一份工程用的是哪份结构模板，只有一处权威：`project.template_uuid`。名字可能出现在三个地方
（锚点的 `template`、库的 `template_name`、以及上一版模板 JSON 里的 `name`），它们的共同身份是
**线索**，只在"库里没有 uuid"时有意义。规范名是「中文名(英文名)」这种写法（例如
`438C-软件设计说明(SDD)`）；认引用时三种写法都试：中文名、英文名、拼接写法，比较前统一做
全角转半角、去空白、不分大小写。

**只认唯一命中**：认不出来、或有两份模板同名，一律按"模板未认到"处理，交给用户去处理，
不猜是哪一份。悬挂的工程照常打开、照常编辑，界面只在状态栏与打开提示里说一句。

"模板未认到"这件事本身的形态：

| 哪里 | 表现 |
| --- | --- |
| 状态栏 | 写「模板未认到」 |
| 打开工程 | 提示里带上那个老名字，让人知道是哪一份没认到 |
| 工程信息 | `templateName` 留空、`legacyTemplateName` 带出老名字（认到之后这一项不再报） |
| 导出 | 另有一套悬挂与缺样式的拦截，不在本页口径内 |

已经认到 uuid 的工程即使库里还留着 `template_name`，界面也不再拿它当"没认到"的证据 ——
那一列是留给下次认引用用的线索，不是状态。

## 5 老库兼容：按 `PRAGMA table_info` 问列、保存时补列

新版本往库里加过两列（`project.template_uuid`、`node.allow_layout_edit`），老库没有它们。
直接用新列的读语句会让老工程整个打不开（`no such column`），所以两边都按"先问列再决定"来写：

| 场景 | 做法 | 缺列的缺省 |
| --- | --- | --- |
| 读 `project` | `projectColumns()` 问一遍，缺的列在 SELECT 里替成空串 | 模板引用回落到名字 |
| 读 `node` | `nodeColumns()` 问一遍，缺的列在 SELECT 里替成常量 | `allow_layout_edit` 当 1（排版开着） |
| 写 `project` | 保存时 `ALTER TABLE project ADD COLUMN template_uuid TEXT NOT NULL DEFAULT ''` | 补完再 UPDATE |
| 写 `node` | 保存前 `ensureNodeColumns()` 补 `allow_layout_edit ... DEFAULT 1` | 补完再整表重写 |

要点：

- **迁移随第一次保存发生**，打开工程不写盘：打开只读、只在内存里认引用；
- 列名问不出来（表不存在、语句报错）时 `tableColumns()` 返回空数组，由调用方给出
  "工程数据异常"这类人话，而不是把驱动层的错误抛到界面上；
- 补列只加不删、只按缺省值加：老库补完之后的形态与新库一致，老版本程序读不了是必然的
  （它不认识新列），所以升级是单向的。

## 6 老工程打开：名字认 uuid 的一次性迁移

库里没有 uuid 时走一次"按名字认模板"，全过程只在内存里，直到保存才落盘：

1. 取线索：先看库里的 `template_name`，再退到锚点里的 `template`；
2. 都没线索就直接返回（这份工程没有可认的东西，不写空 uuid）；
3. 按第 4 节的规则在已加载的模板注册表里找，**唯一命中才算认到**；
4. 认到了：`store.setTemplateUuid(uuid)` 记在这次会话上、锚点对象里换成 uuid、清掉老名字；
5. 认不到：把老名字留在锚点对象里，一个字都不写盘，下次打开还能再认一次。

保存时 uuid 随 `writeProjectRow` 进库、随 `writeAnchor` 进锚点，老库同时补列 —— 这一次保存之后，
工程就与新工程走同一条 uuid 路径了。三条红线：

- 认不出来时**绝不写空 uuid**：写下去就等于把"还没认到"变成一个既成事实，下次没线索可认；
- 认引用是"只在库里没有 uuid 时"的一次性动作，新写入的数据里不出现模板名；
- 悬挂不是错误：工程照常打开、照常编辑，只是导出那头另有拦截。

## 7 字段退役：`copy_group_id` 与"空转字段"

旧版数据模型里有一个重复单元标记 `copy_group_id`（连同树字段、DTO 与一条校验规则）。
它的问题不是"不好用"，而是**一处行为都没有**：界面不显示、复制不看它、导出不看它，
唯一那条"有它就不能复制"的校验也从来没被哪条路走过。

现在的口径是**彻底退役**，而不是留着兼容：

- 建表语句里没有这一列，读写两侧都不碰它，产品里搜不到这个名字；
- 既有工程库里的那一列是被删掉的（整列删），旧版本程序读不了这些库，办法是同版本号重打包；
- **把列加回去等于让一个空转的字段继续锁住数据模型**：只要列在，就总有人以为它在管事，
  数据模型也就得一直为它留着位置（外键、迁移、自检都要跟着它走）。

`node_type` 是另一类：它还在表里，但普通节点一律写空串，等于"这一列只有根节点用得上"。
判据是同一条 —— 有行为、或者暂时还有正在被读的意义，才值得占一列。

## 8 损坏数据的处理口径：认不出来就拒绝载入

内容块的载入分两种毛病，处理方式不同：

| 情形 | 处理 | 为什么 |
| --- | --- | --- |
| `block_type` 认不出来 | **抛错，拒绝载入整个工程** | 类型是块的身份，不知道它是什么就没法安全地读写它 |
| `props_json` 解析不出来、或不是对象 | **抛错，拒绝载入整个工程** | 属性是块的全部内容，读不出来等于块已经坏了 |
| `lock` 取值不认识 | 照常打开，按"不锁"处理，**记一条加载警告** | 锁是加在内容上的约束，丢了它内容还在；模板那边有校验会拦 |

报错把位置说清楚（`节点「标题」(节点id) 第 N 块`），界面上看到的是主进程那句原话，
用户拿着它能去查是哪一块坏了。

**为什么宁可打不开也不跳过。** 跳过看起来"更宽容"，实际是唯一一条会真的弄丢内容的路径：
块没进内存 → 界面看不到它 → 下一次保存是整表重写（`DELETE` 后重新 `INSERT`）→ 这一块从库里
永久消失。锁拦不住，因为它压根没进内存；撤销也救不回来，因为撤销栈里没有它。

对这条口径的两点补充：

- `props_json` 里的**属性值**则宽松得多：缺字段按空值补、类型不对按字符串转（见
  [DESIGN-05-内容块与表格.md](DESIGN-05-内容块与表格.md) 第 8 节）。"属性读不出来"指的不是
  值不好看，而是整个 JSON 不是一个对象；
- 载入警告走 `loadWarnings()`，当前只有 `lock` 一项来路；它随 `treeGetRoot` 的返回带给界面，
  不写盘、不进撤销栈。

## 9 保存与载入的执行形态

- **保存是整份重写**：一个事务里 `DELETE content_block` / `DELETE node`，再递归 `INSERT`。
  代价与工程大小成正比，换来的是"库里的树就是内存里的树"，不会留下半份改动；
- **写盘时机**：编辑只改内存（每次 IPC 变更在内存里同步执行并校验），SQLite 落库只发生在
  显式保存、切换工程与导出前；撤销的粒度与"什么算一步"见
  [DESIGN-06-权限与锁.md](DESIGN-06-权限与锁.md)；
- 保存失败时回滚事务，并把错误交回调用方；**切换工程前的保存失败就不切换**，
  免得改动被静默丢掉；
- 载入时会按现存 id 给发号器播种（`seedIdCounter`），让新节点的数字 id 越过库里已有的最大值，
  避免新旧 id 撞号；
- `open` 之前会先 `close` 当前库，`create` 会删掉同名库文件重建 schema —— 所以新建工程时
  目录已存在就直接报"已存在同名工程"，不会覆盖既有工程。

由此带来的两条使用上的事实：

- **整份重写没有增量安全网**：库里的数据只在保存那一刻与内存对齐，编辑过程中随时关掉进程，
  丢的是"上次保存之后的所有改动"，不会丢成半份；
- **库不是给人手工改的中间产物**：改库绕过写入侧的校验，下次保存就会被内存里的树覆盖掉；
  会改库的只有产品自己与外部工具链，两边共用同一份 `props_json` 口径。

## 10 不在这份口径里的事

写在这里免得被当成缺陷：

- **不存历史**：库只有当前状态，撤销栈在内存里、随进程结束消失；
- **不做文件级锁与并发写**：一个工程开在一个窗口里，靠"切换前先保存"这条约定保证不互相覆盖；
- **不迁移模板**：工程是模板的一份快照，模板后来改了什么都不会进既有工程；
- **不动 `node_type` 之外的历史列**：老库里读得出来就用、用不上就不读，不回填、不删列
  （退役的字段是另一回事，见第 7 节）；
- **实例 JSON 这条通道只到一半**：`packages/core/src/index.ts` 还导出 `buildTreeFromInstance`
  （实例 JSON → 文档树），但仓库里已经没有调用方，而且它不带 `lock`、`allowLayoutEdit`、
  `rowSpans` 这些后加的字段 —— 现在算遗留的兼容面，退不退记在
  [待办与优先级.md](待办与优先级.md) 里；工程库与模板实例化两条主路径都不走它。
