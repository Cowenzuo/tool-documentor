# 模板体系

> 本文写模板的当前设计：身份与目录组织、结构与样式模板各自的字段、两者的配对规则、样式键与骨架、模板编辑器能做什么、校验分几层。
> 模板的加载与导出如何衔接见 [DESIGN-07-导出、题注与图嵌入.md](DESIGN-07-导出、题注与图嵌入.md)，模板编辑器在界面上的位置见 [DESIGN-02-界面结构.md](DESIGN-02-界面结构.md)。

## 1 身份是 uuid

**每份模板的身份是一个 uuid，名字只作展示。** 身份与命名分开之后，"这是不是同一份模板"只由 uuid 决定，名字可以随便改。

| 字段 | 含义 | 约束 |
| --- | --- | --- |
| `uuid` | 唯一身份，**程序生成、永不变、界面不显示** | 必须是合法 uuid；缺了或写坏了整份读不了，不按名字兜底 |
| `cn` | 中文名，主名 | 展示与校验都要求非空 |
| `en` | 英文名，副名 | 可留空；留空时写回要把这个键删掉，不写空串 |

配套的三条约定都收在 `packages/templates/src/identity.ts` 里，**别处不许自己拼**，否则又会长出第二套"按名字认模板"的口径：

- `newTemplateUuid()` 用 Web Crypto 的 `randomUUID`，不用 `node:crypto`——渲染层要跑同一套判定，一旦 import node 内置模块，编辑模式的浏览器包会带上用不了的 shim；
- 目录名就是 uuid，文件名是 `<uuid>.json`（`templateFileName`）。改名不动文件，所以两者都不带名字；
- `displayNameOf()` 取主名，空则退副名，再空则退 uuid 前八位，保证列表里不出现空条目。

**名字只剩一个用途**：老工程（uuid 化之前）的锚点与库表里记的是模板名字符串，形如 `438C-软件设计说明(SDD)`。`legacyNameOf()` 按旧约定把 cn/en 拼回那个写法，`normalizeTemplateName()` 做 NFKC + 去空白 + 小写的归一，只在"把老引用认回 uuid"这一次读取时用。认到之后回到"只认 uuid"，名字不留在任何新写入里。

## 2 目录组织与扫描

模板目录由用户在设置里提供（可以配多个），每个目录下固定两个子目录，名字是硬约定：

```
<模板目录>/
├── structures/<uuid>/<uuid>.json     结构模板
└── styles/<uuid>/<uuid>.json         样式模板（对照表）
    └── <骨架目录>/                    同一目录下的 docx 骨架
```

**没有清单文件。** 要索引就扫目录：`scanTemplateDir()` 返回四样东西——能读的 `structures`、能读的 `styles`、目录名不是 uuid 的 `legacy`、以及整个子目录缺失的 `missing`。判定逐条：

- 目录名不是合法 uuid → 收进 `legacy`，扫描本身**不猜内容**，交给迁移动作去问用户；
- 目录名是 uuid 才认，文件名按它拼；文件读不到、JSON 解析失败、缺 `uuid`，都记成一条 `problem`，该条不加载并出现在加载报告里；
- **目录名与文件里写的 uuid 不一致** → 这份不能当同一份用，按"读不出来"报（`目录名与 uuid 不一致`），不静默按目录名用。

同一个 uuid 出现在多个目录时**保留先加载的那一份**，后一份连同来源目录记进 `skipped`，不静默覆盖。列表按展示名以中文本地化顺序排——目录名是 uuid，扫出来的顺序对人不构成任何意义。

模板目录默认不在本仓库：真身在仓库外的同级目录，由另一个仓库单独管理；本仓库的 `samples/sample-template/` 是自建的合成模板，只供回归与演示。

## 3 结构模板的定义

结构模板给**文档树的形状**：一棵节点树，每个节点带几个开关与一组预置内容块。顶层字段：

| 字段 | 作用 |
| --- | --- |
| `uuid` / `cn` / `en` | 身份与名字 |
| `category` / `description` / `version` | 新建向导的分类筛选、卡片说明与版本 |
| `defaultStyleUuid` | 默认样式，**单值**；空串表示还没选 |
| `root` | 根节点定义（递归） |

节点字段与缺省值：

| 字段 | 含义 | 缺省 |
| --- | --- | --- |
| `nodeType` | `subTitle` / `subtitle` = 列表子标题；其余值程序不读 | 空 |
| `title` | 初始标题 | 空串 |
| `headingLevel` | 标题级别，导出取 `heading.<N>` 样式的那个 N | `1`（根是 0） |
| `description` | 写给文档作者看的填写说明 | 空串 |
| `copyable` / `deletable` | 模板允许复制 / 裁剪这一章 | **`false`**（漏写就是不许） |
| `allowContentBlocks` | 允许编辑这一章的内容块 | **`true`** |
| `allowLayoutEdit` | 允许改块集合、顺序与类型 | **`true`** |
| `children` | 子节点定义 | 空数组 |
| `contentBlocks` | 预置内容块定义 | 空数组 |

`nodeType` 里那几个英文词**程序一个都不读**，界面只认两种用途：层级标题（进章节编号链）与列表子标题（不占编号链，导出按 `subtitle.<深度>` 取样式）。`chapter` / `section` / `repeatable` 只被当作层级标题、值原样留着；认不出的取值会在树的类型标记上原样显示——那多半是拼错了，得让人看见。

**同一父节点下不许混**：一组兄弟要么全是层级标题，要么全是列表子标题。这条是严格限制，理由是列表子标题**下面只能挂列表子标题**（加载器直接拒收），而且列表子标题的样式按算出来的 `subtitle.N` 取、不占章节编号链。新建节点与改类型都要先看这一组是什么：新建时跟父节点的组走，一级给 `chapter`、更深给 `section`；一组已经混着的结构不能靠"一个个改"收拾，界面上给一个**整组改齐**的动作，按多数那一类一次改到位。

内容块定义（`contentBlocks[]`）的字段：

| 字段 | 用在哪 |
| --- | --- |
| `type` | 八种之一：`text` / `image` / `table` / `formula` / `code` / `mermaid` / `orderedList` / `unorderedList` |
| `content` | 文本块正文、图片路径、公式 LaTeX、代码正文、流程图源码都从它取 |
| `caption` | 图片与流程图的题注；表格的表名 |
| `language` | 代码块语言 |
| `rows` / `cols` / `headers` / `data` / `mergeVertical` | 表格块的形状与首行 |
| `items` | 列表块的条目 |
| `lock` | 块锁：`keep`（类型限制编辑）/ `readonly`（只读），另有已作废的 `type` |

`lock` 不写就是不锁；**取值不认识时按不锁处理**，并把原文写进加载报告的 `warnings`——静默按不锁处理会让人以为锁生效了。锁的语义与两侧取交见 [DESIGN-06-权限与锁.md](DESIGN-06-权限与锁.md)。

## 4 样式模板的定义

样式模板给**版式**：一张"逻辑键 → styleId"的映射表（stylemap），加一个 docx 骨架目录。

| 字段 | 作用 |
| --- | --- |
| `styleMap` | 逻辑键 → 骨架 `styles.xml` 里的 styleId。**必须有**，缺了整份不加载 |
| `docxFolder` | 骨架文件夹名，相对模板自己那个目录 |
| `captionNumbering` | 题注编号方式，可选；缺省等于全按 `auto` |
| `version` / `description` | 展示用 |

`styleMap` 的键是**程序拼 DOCX 时查的名字**（`heading.1`、`table.header`…），值是骨架里的 styleId。程序不写死任何 styleId，换一套骨架只要换这张表。

题注编号有三种方式，逐种题注（表题 `table`、图题 `figure`）各选一个：

| 取值 | 号从哪来 |
| --- | --- |
| `auto` | 由 Word 按样式编号（题注样式自带 `numPr` 多级列表），导出时剥离题注文本里的手写序号 |
| `static` | 序号写在题注文字里，导出原样保留，样式不再编号 |
| `field` | 导出为题注域 `{ STYLEREF 章节样式 \n }-{ SEQ 标签 \s 层级 }`，章节号随标题、序号按节重启，不占标题的多级列表 |

`field` 模式还要 `chapterStyleNames`：`STYLEREF` 只认样式在界面上的**本地化名称**（中文 Word 为「标题 N」），用 styleId 或骨架里的英文名都取不到，所以由模板显式给出。没配时给一条 warn（英文版 Word 算不出章节号），解析不到时该部分退化为导出时算好的静态文本。域的实现与硬约束见 [DESIGN-07-导出、题注与图嵌入.md](DESIGN-07-导出、题注与图嵌入.md)。

加载时还会从骨架 `numbering.xml` 的**第一个 `abstractNum`** 读出各层级的起始编号（`headingStarts`），供 `field` 模式算题注章节号的缓存值（报告从第 4 章起编号时要用）。读不到就是 `undefined`，校验给一条 warn，题注章节号从 1 起算。

## 5 配对规则：默认样式

结构与样式之间**只有一根线**：结构模板顶层的 `defaultStyleUuid`，值是样式的 uuid。解析规则只写在 `packages/templates/src/resolve.ts`，加载器与界面都调它，不各自判一遍。解析结果分三种状态，调用方的说法不一样：

| 状态 | 含义 | 界面与下游怎么办 |
| --- | --- | --- |
| 正常 | 写了 uuid，且目录里有这份、也读得出来 | 导出默认选它，试跑用它 |
| `unset` | 没写默认样式（空串） | 导出时先让用户选一份；试跑直接拒，说清"没配默认样式" |
| `dangling` | 写了 uuid，但目录里找不到这份（或那份读坏了） | **允许的状态**，不拦加载；界面标「默认样式找不到 · 可能已被删除，重选一份」 |

**悬挂是允许的，这是有意设计**：样式可以被独立删除，删掉之后用它的结构照样能打开、能编辑，只是没有默认样式。导出对话框列出模板目录里**能读出来的全部样式**，默认选中结构里写的那一份；悬挂时没有任何一份带"默认"标记，于是默认落在第一份上，用户可以改选——导出不会被拦住。只有试跑要拒，因为试跑没有"让用户挑"这一步。

"读坏了的那份不算能用的样式"也是这条规则的一部分：宁可报悬挂，也不要拿半份样式去导出。

## 6 样式键

一份 stylemap 里认得的逻辑键共 **22 行**，其中 **18 个是程序真正读的**：

| 分区 | 键 | 读不读 |
| --- | --- | --- |
| 标题 | `heading.1` … `heading.7` | 读 |
| 列表子标题 | `subtitle.1` … `subtitle.3` | 读 |
| 正文 | `body` | 读 |
| 图片 | `figure`、`figure.caption` | 读 |
| 表格 | `table.caption`、`table.header`、`table.body` | 读 |
| 列表 | `list.ordered.1`、`list.unordered.1` | 读 |
| 列表高阶 | `list.ordered.2/3`、`list.unordered.2/3` | **不读**（配了只提示不生效） |

`SUPPORTED_STYLE_KEYS` 就是上表里"读"的那 18 个，**校验按这个固定全集查缺键**，与任何结构模板无关：样式齐了就任何结构都能配它导出。这条口径取代了早期"按结构用到什么块推导必需键"的做法——推导没有意义，完整性只该有一把尺子。

**回退只有一条**：`figure` 没配时，图片与图形段落的样式回退用 `body`。其余键没配就按 Word 默认样式输出，导出时另有一条「样式未生效」的告警。键与用途的对应关系来自序列化器，改序列化口径时两处一起改。

界面上这张表叫**样式对照表**，每行回答三件事：这一行管什么（用途）、现在指向谁（映射）、没配或配错了会怎样（状态与回退）。行的状态有五档：

| 状态 | 意思 |
| --- | --- |
| `ok` | 配了，且指向的样式在骨架里 |
| `dangling` | 配了，但骨架 `styles.xml` 里没有这个 styleId |
| `inert` | 程序不读这个键，配了不生效 |
| `unset` | 没配（用到时按默认样式或按回退键输出） |
| `unchecked` | 骨架没读到（或一个 styleId 都没有），这一行没得核对 |

骨架没读到时不报"样式不存在"——那是"没核对"，不是"配错了"，缺骨架这件事由校验自己报。表外的键（手写时拼错的 `heading.10` 之类）也照样列出来，落在「其他」分区并明说程序不读；藏起来作者就不知道自己配的那一行为什么不生效。界面上还会并列一份"骨架里有、这份表没人用"的 styleId 清单，方便发现漏配——按**草稿**实时算，改一行立刻从清单里消失。

## 7 骨架

骨架就是导出时当底的那份 docx 目录（解包状态）。**必需部件五个，缺一个就是 error**：

```
[Content_Types].xml
_rels/.rels
word/document.xml
word/styles.xml
word/numbering.xml
```

`word/_rels/document.xml.rels` **不在必需表里**：缺它时 `styles.xml` 与 `numbering.xml` 从主文档到达不了，Word 可能当它们不存在——但导出侧会补出这两条关系，所以只报一条警告，不判不可用（四套真实样式模板都自带该部件，风险落在自定义与极简骨架上）。

校验与界面要读的骨架事实由 `parseSkeletonIndex()` 一次算出：

- **字面扫描** `styleId="..."` 得到的 id 集合——这是判定用的口径，与加载器同法。刻意不做 XML 解析：解析器对 `<w:style>` 之外的 styleId 引用行为不一致，两处必须同法；
- **可读样式表**（给人看的下拉选项）：styleId、样式名、段落或字符、是否默认、`basedOn`、字号（`w:sz` 是半磅，24 → 12 磅）；
- **这条样式带不带自动编号**：`w:numPr` 里给了非 0 的 `w:numId` 才算带（`w:numId="0"` 是 OOXML 里"取消编号"的写法）。判题注靠的就是它——`auto` 模式的号来自样式多级列表，样式没带号时 `auto` 出不来号。

**骨架里的字节程序一个都不改。** 导入样式只是把 `.docx` 解包、或把一个已解包的目录整份复制进来，随后只做部件检查；程序拼装 `styles.xml` 与 `numbering.xml` 等于重造 Word 的版式系统，风险与收益不成比例。

## 8 模板编辑器能做什么

模板编辑器是软件内的入口（界面上是整页，见 [DESIGN-02-界面结构.md](DESIGN-02-界面结构.md)），主进程侧是 `services/template-editor-service.ts`：**只动模板目录里的 JSON 与目录**，不依赖工程库、不进撤销栈、不写 `.dproj`。

| 动作 | 做了什么 |
| --- | --- |
| 快照 | 扫全部配置目录：目录级问题（目录不存在、子目录缺失、目录名不是 uuid）+ 结构/样式条目（错误与提示计数、逐条结论）。样式条目另带 `usedBy`：哪些结构把它写成了默认样式 |
| 新建结构模板 | uuid 由程序生成；写身份、`version: '1.0'`、可选 `defaultStyleUuid`，根节点是 `{ title: 模板名, headingLevel: 0 }`。写前自校验，出现 error 就失败、不落盘 |
| 读结构模板 | 读 JSON 原文 + 校验结论。界面按字段编辑，未认识的字段原样保留 |
| 写结构模板 | 先校验，**有 error 就抛错不落盘**；通过才原子写 |
| 读样式模板 | stylemap 原文 + 骨架事实 + 对照表行 + 骨架里没人用的 styleId + `usedBy` |
| 写样式模板 | 只动 `styleMap` 与 `captionNumbering` 这些字段，其余键与顺序保留；同样是零 error 才写 |
| 导入样式 | 源可以是 `.docx` 或已解包的骨架目录，两条路走同一套检查 |
| 改名（结构 / 样式） | **只写模板自己那一个 JSON**：不碰目录名、不碰文件名、不碰任何引用 |
| 删除（结构 / 样式） | 删整份 `structures/<uuid>/` 或 `styles/<uuid>/`（样式含骨架） |
| 试跑 | 用这份结构 + 它的默认样式，**真的导出一份 .docx** |
| 迁移 | 把旧格式目录改成 uuid 格式，见第 11 节 |

几条值得单独说的：

- **导入样式的"全有或全无"**：先铺骨架（`.docx` 走 JSZip 解包，条目名写出目标目录之外直接判错；目录走整份复制），再查必需部件与"读不读得到 styleId"；任何一步没成就把刚铺开的目录整份删掉，不在模板目录里留半份样式。成功后按**样式名做一次模糊匹配**生成映射草稿（`draftStyleMap`），认出来的键先填上、认不出的留空待作者填——绝不编一个 styleId 出来。四个程序不读的高阶列表键不生成草稿，填了不生效，列出来只会误导；标题与列表子标题这两组只认完全相等（「列表子标题1」的结尾正好是「标题1」，允许"含"的话会把 `heading.1` 抢走）；
- **试跑是验收判据**：有 error 的模板先拒；默认样式未设或悬挂也拒。产物落在应用数据目录的 `template-trials/<uuid>/<uuid>-<时间戳>.docx`，可以直接用 Word 打开回读。**判据是导出链路的样式告警为零**（`styleWarnings`，即"样式未生效"那一类），比任何静态检查都硬。

## 9 写盘纪律

- **原子写**：先写同目录下的临时文件（`.<文件名>.tmp-<pid>-<时间戳>`），再改名覆盖。任何一步失败都清掉临时文件，不留半截；
- **不写 `.bak`、不留备份目录、不回滚**：可恢复性归版本控制，模板目录通常就在 git 里，影子副本只会制造"删了没删干净"的假象。程序也**不做模板文件的自动提交**——界面上要能看出这个目录受版本控制，保存完由作者自己提交；
- **缩进与行尾按原文件认**：缩进看第一个缩进行（认不出退回 2 空格），原文件是 CRLF 就写回 CRLF，免得整份文件行尾翻转；
- **写前必须零 error**，否则抛错、不落盘，错误原文原样回给界面（点「详情」看全文）；
- 只有用户点保存时才写文件；改字段、加节点、改映射都只落在内存草稿里。

## 10 校验的分层

规则分四层，分层的理由是**渲染层不能碰 `node:fs`**：

| 层 | 位置 | 碰 fs | 谁用 |
| --- | --- | --- | --- |
| 样式规则（判定与文案） | `packages/templates/src/style-rules.ts` 的 `validateStyleMap` | 否 | 主进程与渲染层跑**同一份** |
| 结构规则 + 读盘 | `packages/templates/src/validate.ts` 的 `validateStructureTemplate` / `validateStyleTemplate` | 是 | 加载报告、模板列表徽标、保存闸门、试跑 |
| 样式键元数据与对照表行 | `style-keys.ts` 的 `buildStyleMapRows`、`style-match.ts` 的 `draftStyleMap` | 否 | 界面 |
| 结构规则的渲染层镜像 | `components/template/templateValidate.ts` | 否 | 编辑时的即时结论 |

前两层的关系是：`validateStyleTemplate` 读盘把骨架读成"事实"（目录在不在、缺哪些部件、有哪些 styleId、起始编号是多少），再把事实交给不碰 fs 的那份规则去判。所以样式侧的判定与文案**只有一份实现**，渲染层通过 `@documentor/templates/style-rules` 与 `style-keys` 直接 import 它（`styleDraft.ts` 就是这么做的），改了映射当场标红、有 error 不许保存。

**结构侧是个刻意的例外**：`validate.ts` 顶层 import 了 `node:fs`，出口 `index.ts` 还会带出 `manager.ts` → `@documentor/core`，渲染层打进浏览器包时 node 内置模块会被换成只有 default 的 shim，具名导入当场报错。所以 `templateValidate.ts` **镜像**了单份结构模板能判的规则（身份、节点开关、内容块字段、表格形状、锁取值），只用于决定按钮亮不亮与问题列表长什么样；**保存仍以主进程的校验为准**。两份规则靠人工对齐，改动时要一起改 —— 没有"两边结论逐条一致"的对照测试兜住，这是当前状态，不是设计目标。

`TemplateManager.validateStyleTemplate(styleDef)` 与 `validate.ts` 里那个同名函数**不是一回事**：前者只逐条比 `styleMap` 与骨架里的 styleId，不查样式键全集，且仓库里已经没有任何调用点（界面与保存闸门走的都是 `validate.ts` 那份）。留着它只是模板包的一个兼容面，要不要清掉记在 [待办与优先级.md](待办与优先级.md) 里。

校验的输入一律是**模板 JSON 原文**，不是加载器解析后的 `TemplateDef`：判的是原文（节点上有没有写 `lock`、`headingLevel` 是不是整数、块上有没有多写节点级字段），这些信息在解析成 `TemplateDef` 时就丢了。结论的形状是 `{ level: 'error' | 'warn', rule, path, message }`：`rule` 是稳定的规则标识供分组过滤，`path` 是 JSON 路径（`root.children[2].contentBlocks[0].lock`）或字段/部件名，`message` 是可以直接展示给模板作者的一句人话。几条典型的结论：

- 节点上写了 `lock`、或块上写了 `copyable` 这类节点级字段 → **error**：位置错了程序不读，界面选了也不生效；
- `headingLevel` 不是非负整数 → error；超过 9 → warn（层级太深）；
- 表格的 `cols` 非法、`headers` 与 `cols` 列数对不上、`data` 行列数不齐 → error；`rows` 与正文行数对不上 → warn（两种口径都接受：正文行数，或含表头的行数 +1）；
- 样式缺全集里的键 → error；指针指向骨架里不存在的 styleId → error；骨架必需部件缺失 → error；缺关系表 → warn；
- 题注：`field` 模式没配章节样式名 → warn；缺 `captionNumbering` 且题注样式没带多级列表编号 → warn「题注编号不会出现」。说结果，不说"你没配 `captionNumbering`"——那半句是废话。

## 11 旧格式与迁移

**旧格式不并存**，靠模板编辑器里的迁移动作一次改完。识别条件是**目录名不是合法 uuid**（`structures/` 与 `styles/` 各自扫）。迁移**先样式后结构**，因为结构的引用要按老的文件键换成新分配的样式 uuid，样式得先落地：

1. 老文件名有约定：`<老 id>-stylemap.json` 与 `<老 id>-structure.json`；认不出就取目录里唯一那份 `.json`，取不到就跳过这一条并报出来；
2. 老模板只有一个 `name`，写法常是「中文名(英文名)」：按括注拆成 `cn` 与 `en`，拆不出就把老目录名当 `en`，留个可追溯的英文键；
3. 样式：分配新 uuid，写身份 + `version`/`description` + `docxFolder` + `styleMap` + `captionNumbering`，**骨架整份搬进新目录（一个字节不改）**，删掉老目录；同时把老目录名、`<老名>-stylemap`、`<老名>-style` 与老 `name` 都登记到一张老键 → 新 uuid 的表上；
4. 结构：把老的 `styleTemplate`（单值）或 `styleTemplates` 里第一个认得的键换成新样式 uuid，写进 `defaultStyleUuid`。**换不到就留空**并进 `restyle` 列表，提示「旧文件里写的样式 X 不在这个目录里，默认样式留空待选」——由用户重选，不猜；
5. 最后删掉模板目录顶层的 `manifest.json`（旧格式的清单），并回报它删没删。

一份失败只影响它自己：半份新目录撤掉，老目录留在原处，原因进 `skipped` 报出来让人处理。迁移后每份模板都能加载，校验结论与迁移前一致。

## 12 红线

- **uuid 是唯一身份**：目录名、文件名的推导都收在 `identity.ts`，别处不许自己拼；名字不参与匹配，只有"把老工程引用认回 uuid"那一次读取例外；
- **悬挂是允许的状态，不是错误**：删掉一份样式不该让用它的结构打不开。但导出与试跑都要有说法——导出让用户重选，试跑直接拒；
- **样式完整性按软件支持的全集查，不按结构推导**。任何结构配任何样式都能导出，这是"不存在不匹配的样式模板"这句话的全部依据；
- **骨架里的字节一个都不改**。改骨架前先想清楚会不会动到用户模板的版式；
- **模板不随软件分发**。发行包里没有模板，`samples/` 那份是自建合成模板，只供回归；
- **程序不写备份、不自动提交**：模板目录的可恢复性归版本控制。
